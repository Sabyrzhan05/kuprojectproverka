# API стенда: запросы сервера и выгрузка для личного кабинета

Документ для разработчика, которому передаётся стенд расчёта коммунальных услуг апарт-отеля TOR'RE Astana: какие запросы
принимает сервер стенда, что они меняют в базе и в каком виде уходят квитанции в личный кабинет собственника. Соответствует
коду на 06.10.2026, схема выгрузки — 1.6.

Источник истины — код. Маршруты — `server/index.js` (функция `handle`); хранилище и сборка помещения — `server/db.js`;
закрытие месяца, корректировки, переплата — `server/periods.js`; импорт показаний — `server/import.js` и
`server/parse_import.py`; очистка данных месяцев — `server/clean.js`; начисления за месяц — `server/accruals.js`; расчёт и
документы выгрузки — `engine/calc.js`. Если текст расходится с кодом, прав код, а документ исправляется.

Разделы:

1. Общие соглашения — адрес, формат, заголовки, коды ответов, журнал, копии базы.
2. Данные — объекты, которые ходят в запросах.
3. Запросы — все маршруты сервера.
4. Выгрузка для личного кабинета — документ схемы 1.6.
5. Расчёт без сервера.

## 1. Общие соглашения

### 1.1. Адрес, запуск, база

- Адрес: `http://localhost:3000`. Сервер слушает только `127.0.0.1` — с других компьютеров недоступен.
- Запуск: `node server/index.js` (`npm start`; на Windows — `Запустить.bat`). Внешних зависимостей нет. Для импорта показаний
  нужен Python 3 с пакетами `openpyxl` и `xlrd`.
- Переменные окружения: `PORT` — порт (по умолчанию 3000); `TORRE_DATA` — папка базы (по умолчанию `data/` проекта).
  Проверочные запуски — только на копии базы: `TORRE_DATA=<папка с копией> PORT=<порт> node server/index.js`.
- База — JSON-файлы, по одному на таблицу, в папке базы. Там же: `files/` — вложения договоров, `backup/` — копии базы,
  `log_archive.json` — архив журнала. Запись таблицы атомарная: временный файл, сброс на диск, переименование поверх.
- Сервер держит таблицы в памяти с первого чтения. Правка файлов базы в обход сервера не видна до перезапуска.
- Один процесс, один поток. Пока выполняется расчёт месяца (`GET /api/accruals`, 0,5–1,5 с) или импорт (несколько секунд),
  другие запросы ждут.
- При запуске, до приёма запросов, сервер приводит базу к действующим правилам, если в ней есть что приводить:
  - начальное показание каждого прибора — конечное за прошлый месяц (копия базы `pre-start-carry`);
  - ручные пометки разграничения прежнего формата (на приборе, тепло — на помещении) переносятся к последнему собственнику
    помещения (копия базы `pre-start-marks`).

  Обе операции пишут журнал. Если приводить нечего, база не меняется.
- Остановка — Ctrl+C: таблицы из памяти записываются на диск.

### 1.2. Формат обмена

- Тела запросов и ответов — JSON в кодировке UTF-8. Исключения — вложения (`/api/files`), выгрузка базы файлом
  (`/api/dump`), движок (`/engine/calc.js`) и файлы интерфейса.
- Тело запроса читается целиком как строка UTF-8; предел — 60 млн знаков. Пустое тело равно `null`.
- Ответы JSON идут с заголовками `Content-Type: application/json; charset=utf-8` и `Cache-Control: no-store`.
- Ошибка — объект `{"error": "текст для человека"}`. У отдельных ответов есть дополнительные поля (`conflict`, `errors`) — они
  указаны в описании запроса.
- Заголовков CORS сервер не отдаёт: страница с другого адреса ответы сервера не прочитает.

### 1.3. Даты, месяцы, числа

| Что | Формат | Пример |
|---|---|---|
| Дата | строка `ГГГГ-ММ-ДД` | `2026-06-15` |
| Месяц (период) | строка `ГГГГ-ММ` | `2026-06` |
| Отметка времени (`at`, `closedAt`, `generatedAt`, `issuedAt` и др.) | ISO 8601, время по Гринвичу | `2026-10-06T13:00:37.818Z` |
| Имя копии базы | время по Гринвичу | `2026-10-06T13-00-11_close-2026-06` |
| Время вложения `at`, имя файла вложения | местное время сервера, без пояса | `2026-10-06T18:01` |
| Деньги в строках квитанций | число, тенге с копейками | `39022.83` |
| К оплате, переплата, разница корректировки, зачёт | целые тенге | `39023` |

- Даты в расчёте сравниваются как строки. Поэтому сервер принимает только `ГГГГ-ММ-ДД` и только существующую дату:
  `12.05.2025` и `2026-02-30` — ошибка 400.
- «С» и «по» везде включительно. `null` у «с» — с начала учёта, у «по» — бессрочно.
- Показания приборов — числа. Строку с запятой («297,388») сервер приводит к числу.
- Вводные месяца в настройках хранятся строками так, как их ввёл оператор («3 299 963,73», «0,2121»). Расчёт читает их
  как числа: пробелы и запятая допускаются.
- Единицы: вода — м³, электроэнергия — кВт·ч, тепло — Гкал, площадь — м².

### 1.4. Заголовки записи. Кто работает

Запрос к `/api/…` любым методом, кроме `GET` и `HEAD`, принимается, только если в нём есть хотя бы один из заголовков:

| Заголовок | Кто присылает | Значение |
|---|---|---|
| `X-Tab` | пульт — с каждой записью | номер вкладки браузера, произвольная строка |
| `X-User` | пульт — когда в верхней полосе выбрано, кто работает; служебные скрипты | имя работающего, закодированное `encodeURIComponent` (в заголовках допустима только латиница) |
| `Content-Type: application/json` | служебные скрипты и другие клиенты | — |

Без них ответ — `403 {"error": "запись принимается только от стенда"}`. Это защита от записи со сторонней страницы,
открытой в том же браузере, а не вход. Паролей, ролей и прав в стенде нет: вход и права делает разработчик кабинета.

Заголовок `X-User`:

- пишется в журнал полем `by` («кто»). Без заголовка поля `by` у записи журнала нет;
- по нему проверяется, кто может выполнить действие: открыть закрытый месяц и очистить данные месяцев могут только
  «Руководитель» и «Бухгалтерия». Список работающих — `settings.users`: `[{name, dept}]`, где `dept` — `""` у «Руководителя»,
  `k` у «Бухгалтерии», `r` у «Работы с собственниками». Имени нет в списке или у него `dept: "r"` — отказ;
- права на открытие месяца заново и на очистку месяцев проверяются по `X-User`, а без него — по полю `by` из тела;
- «кто» в записях закрытия, открытия, корректировок, зачётов и возвратов (`closedBy`, `reopenedBy`, `by`) — поле `by` из тела,
  иначе `X-User`, иначе «оператор». В журнале — всегда `X-User`.

Заголовок `X-Tab` участвует в проверке версии помещения (`_rev`, раздел 3.4): записи одной вкладки подряд не считаются
конфликтом.

### 1.5. Коды ответов

| Код | Когда |
|---|---|
| 200 | успех |
| 400 | ошибка ввода: неверная %-кодировка адреса; нет обязательного параметра; месяц, дата или показание не в формате; неизвестный ресурс прибора или программа управления; пустое тело; любой отказ акта замены прибора; ошибки импорта |
| 403 | запись без заголовков стенда; таблица не редактируется целиком; очистка месяцев не «Руководителем» и не «Бухгалтерией» |
| 404 | нет помещения, вложения, копии базы; месяца нет в стенде (`/api/accruals`); неизвестный запрос; файл интерфейса не найден |
| 405 | действие с периодом запрошено методом `GET` |
| 409 | нельзя по правилам: закрытый месяц, замок акта замены, порядок закрытия, корректировки, зачёты; помещение изменено после загрузки (`conflict: true`); копию вернуть нельзя; копия на Google Диск уже делается; вложение ещё в договоре |
| 413 | вложение больше 25 МБ |
| 415 | тип вложения не принимается |
| 500 | сбой сервера. Кроме того: тело запроса — не JSON (у запросов `/api/period/…` — 409); месяц не `ГГГГ-ММ` в `/api/state` и `/api/unit`; «Выгрузка остановлена — в данных ошибка» в `/api/accruals`; ошибка копии на Google Диск |

Проверки выполняются до первой записи: при отказе база не меняется. Исключение — сбой записи файла (500): запись могла
пройти частично.

Неизвестный путь или метод — `404 {"error": "неизвестный запрос <МЕТОД> <путь>"}`.

### 1.6. Журнал изменений

Таблица `log`. Запись журнала:

| Поле | Что |
|---|---|
| `at` | время, ISO по Гринвичу |
| `unit` | номер помещения; `*` — весь дом (тарифы, вводные месяца, закрытие месяца и т. п.) |
| `what` | что изменено, словами: «площадь», «текущее показание · Электро 306386», «период 2026-06 закрыт» |
| `before`, `after` | было и стало, строками |
| `period` | месяц запроса; если его нет — месяц, выбранный в настройках |
| `by` | кто работал (`X-User`); нет заголовка — поля нет |
| `kind` | `reg` — правка реестра (собственники, владение, контакты, представители, договоры управления). По этой метке бухгалтерия видит новые правки реестра |

Что пишется в журнал:

| Действие | Записи |
|---|---|
| `PUT /api/unit/:n` | по записи на каждое изменённое поле: помещение, договоры управления, собственники, контакты, ручные пометки разграничения, приборы, показания, договоры разграничения, акты опломбировки, вложения; создание и удаление записей; пометки на удаление и их снятие |
| `DELETE /api/unit/:n` | «помещение удалено» |
| `POST /api/unit/:n/replace` | «акт замены · старый прибор → новый»; перенос ручной пометки на новый счётчик |
| перенос начала месяца — после записи помещения, акта замены, импорта и при запуске | «начальное показание · прибор (конец прошлого месяца ГГГГ-ММ)» |
| `PUT /api/table/tariffs` | по записи на добавленную, изменённую, удалённую строку тарифа |
| `PUT /api/table/settings` | переключатели «применять договоры разграничения» и «компания платит КУ за помещения в управлении»; вводные месяца (счета-фактуры, нужды ЭК, «ЭК берёт из ОДН», общая площадь здания); доходные месяца |
| `POST /api/import` | «импорт показаний · прибор» на каждый изменённый прибор; «импорт тепла ГГГГ-ММ» |
| закрытие и открытие месяца | «период ГГГГ-ММ закрыт [принудительно]», «период ГГГГ-ММ открыт заново» |
| корректировка | «корректировка ADJ-…» на каждый месяц; изменённые начальные показания следующего месяца (каскад) |
| зачёт, возврат переплаты, их отмена | по записи |
| `POST /api/restore` | «база возвращена к копии» |
| `POST /api/clean-months` | «очистка данных месяцев · …» с итогами удаления |

Не пишется: чтение; копии базы; приём и удаление файла вложения (в журнал попадает включение файла в договор через
`PUT /api/unit`); `PUT /api/table/external` и `PUT /api/table/unit_names`; копия на Google Диск; служебные поля настроек
(выбранный месяц, отметки «проверено» и «просмотрено»).

Журнал длиннее 25 000 записей: самые старые уходят в `<база>/log_archive.json`, в журнале остаются 20 000 последних.

### 1.7. Копии базы

Копия — папка `<база>/backup/<ГГГГ-ММ-ДДTчч-мм-сс>[_<метка>]`. Время в имени — по Гринвичу; две копии в одну секунду
получают окончание `-2`, `-3`. В копии — файлы всех таблиц базы, какие есть. Вложения (`files/`) и архив журнала в копию не
входят.

Когда делается копия:

| Действие | Метка |
|---|---|
| `POST /api/backup?tag=…` (кнопка «Копия базы») | метка из запроса |
| `DELETE /api/unit/:n` | `del-<помещение>` |
| `POST /api/import` | `pre-import-<ГГГГ-ММ>` |
| `POST /api/period/:p/close` | `close-<ГГГГ-ММ>` |
| `POST /api/period/:p/reopen` | `reopen-<ГГГГ-ММ>` |
| `POST /api/restore` | `before-restore` — состояние до возврата |
| `POST /api/clean-months` | `перед очисткой месяцев <ГГГГ-ММ …>` |
| запуск сервера, если база приводится | `pre-start-carry`, `pre-start-marks` |

Копия не делается при записи помещения, акте замены, правке тарифов и настроек, корректировке, зачёте и возврате.

Хранятся 30 последних копий; лишние удаляются, начиная со старых, при создании новой. Копии, имя которых оканчивается на
`_исходная`, не удаляются. Метка очищается: знаки пути и служебные знаки заменяются на «-», длина — до 80 знаков.

Возврат к копии — раздел 3.21. Закрытые месяцы, корректировки и журнал копия не возвращает никогда.

### 2.2. Помещение в запросах (`Unit`)

Сервер собирает помещение из таблиц за месяц запроса (`buildUnit`) и раскладывает обратно при записи (`putUnit`).

| Поле | Тип | Что |
|---|---|---|
| `n` | строка | номер помещения: «5017», «НП1», «2.004»; не меняется |
| `fl` | число | этаж |
| `t` | строка | тип |
| `area` | число | площадь, м² |
| `inodn` | логическое | участвует в ОДН |
| `prog`, `cno`, `cdt` | | договор управления, действующий в месяце запроса (из пересекающих месяц — начавшийся позже); `prog: "none"` — не в управлении. Вычисляет сервер |
| `progs[]` | | договоры управления: `prog` (`none`, `hybrid` — гибридная, `trust` — доверительная, `share` — долевая), `cno` (номер), `cdt` (дата), `from`, `to`, `del` |
| `fio` | строка | последний собственник без пометки на удаление. Вычисляет сервер |
| `owners[]` | | собственники: `fio`, `from`, `to`, `del`, `rz`, `phones[]`, `emails[]`, `reps[]` (`fio`, `phones`, `emails`, `basis`, `note`) |
| `meters[]` | | приборы с показаниями (ниже) |
| `rz` | объект | договоры разграничения по ресурсам: `w` — вода, `e` — электроэнергия, `h` — тепло; в каждом — массив договоров (ниже) |
| `del` | строка или `null` | пометка помещения на удаление |
| `_rev` | строка | отпечаток помещения, 16 знаков — защита от перезаписи чужих правок |

Ручная пометка разграничения собственника `rz`: `{w?: логическое, h?: логическое, e?: {<номер прибора>: логическое}}`. `w` —
все водяные приборы помещения, `h` — тепло, `e` — электросчётчик. `true` — «разграничено вручную», `false` — «в счёт УК
вручную»; ключа нет — по договору разграничения. Пометка действует в дни владения своего собственника.

Прибор:

| Поле | Что |
|---|---|
| `id` | номер прибора `помещение\|ресурс\|серийный номер` (без серийного номера — `noSN`); при совпадении — с окончанием `#2`, `#3` (у прибора, поставленного актом замены, — `#<число>`). Постоянный, пока не меняются ресурс и серийный номер |
| `res` | `hvs` — холодная вода, `gvs` — горячая вода, `ee` — электроэнергия |
| `sn` | серийный номер |
| `k` | коэффициент трансформации, по умолчанию 1 |
| `bill` | участвует в расчётах; `false` — не начисляется |
| `transit`, `note` | прежняя метка «транзит» (расчётом не используется), примечание |
| `from`, `to` | установлен, снят — ставит акт замены или оператор |
| `del` | пометка на удаление |
| `prev`, `cur` | начальное и конечное показание месяца запроса |
| `midRead` | показание на дату договора разграничения (хранится; по действующему правилу «договор разграничивает месяц целиком» расчётом не используется) |

| `hist` | показания всех месяцев: `{ГГГГ-ММ: {prev, cur, midRead, ownRead, lockPrev, lockCur, prevSrc, prevNote}}` |

Договор разграничения:

| `note` | описание |

### 2.4. Тарифы (`tariffs`)

| Поле | Что |
|---|---|
| `svc` | услуга: `water_supply` — водоснабжение, `water_drainage` — водоотведение, `electricity` — электроэнергия, `heating` — теплоэнергия, `maintenance` — техобслуживание МОП, ₸/м², `capital_repair` — взносы на капремонт, ₸/м² |

| `vat` | НДС, % |

| Поле | Что |
|---|---|
| `period` | месяц |

### 2.7. Зачёт и возврат переплаты (`offsets`)

| Вид | Поля |
|---|---|
| Зачёт в квитанцию (`type` `KU` или `EK`) | `id` (`OFF-<месяц>-<помещение>-<k>-<…>`), `unit`, `fio`, `ownFrom`, `amount` (целые тенге), `period`, `type`, `note`, `at`, `by`. В квитанции месяца — строка «Зачёт переплаты» на `−amount` |
| Возврат деньгами (`type` `REFUND`) | `id` (`REF-<помещение>-<k>-<…>`), `unit`, `fio`, `amount`, `date`, `month`, `type`, `note`, `at`, `by`. Квитанций не меняет; поля `period` нет |

Переплата собственника (`credits`) начисляется, когда квитанция собственника уходит в минус (на закрытии месяца), и по
корректировочным квитанциям «к зачёту». Остаток = начислено − зачтено − возвращено. Сама переплата никуда не зачитывается:
зачёт и возврат оформляет оператор.

### 3.1. `GET /api/state`

Все данные месяца — то, что загружает пульт при открытии и смене месяца. Этот же объект — вход движка (раздел 5).

Параметры: `period` — `ГГГГ-ММ`, по умолчанию `settings.period`. Формат не проверяется: значение не `ГГГГ-ММ` даёт 500.

Ответ 200:

| Поле | Что |
|---|---|
| `settings` | настройки целиком (2.3) |
| `period` | месяц, за который у приборов собраны `prev` и `cur` |
| `rows` | все помещения (`Unit`, 2.2), включая помеченные на удаление; у каждого — `_rev` |
| `tariffs`, `external`, `unitNames` | тарифы, доходные контрагенты (образец), подписи помещений |
| `periods` | месяцы, по которым есть показания |
| `caps` | что умеет сервер: `del`, `contacts`, `who`, `files`, `rev`, `refund`. Пульт без нужного признака не даёт делать то, что сервер не сохранит |
| `closed` | снимок месяца целиком (2.5), если месяц закрыт; иначе `null` |
| `closedPeriods`, `lastClosed` | закрытые месяцы; последний закрытый или `null` |

| `credits` | переплаты всех собственников: `[{source, unit, fio, period, code, type, amount, adj}]`; `source` — `close` (закрытие) или `adjustment` (корректировка) |

### 3.2. `GET /api/accruals`

Параметры: `period` — `ГГГГ-ММ`, обязателен.

Ответ 200 — документ выгрузки для личного кабинета (раздел 4), JSON без отступов, около 1 МБ. Открытый месяц — расчёт по
текущим данным, `status: "open"` (черновик). Закрытый месяц — из снимка, `status: "closed"`, вместе с корректировочными
квитанциями. Время ответа: открытый месяц — около 1,5 с, закрытый — около 0,5 с.

Месяц «есть в стенде», если по нему есть показания, вводные месяца (`settings.byPeriod`) или снимок закрытия.

| 500 | `{"error": "Выгрузка остановлена — в данных ошибка:\n…", "errors": [все ошибки]}` — расчёт отдельных помещений не выполнен (например, плательщик не из трёх значений); документ не выдаётся |

### 3.4. `PUT /api/unit/:n`

Записать помещение. `PATCH` работает так же.

Параметры: `period` — месяц, к которому относятся `prev`, `cur`, `midRead`, `ownRead` в теле; по умолчанию `settings.period`.

Тело — `Unit` целиком или часть его разделов.

- Разделы `progs`, `owners`, `meters`, `rz` записываются целиком, если присланы: прежние записи помещения в разделе
  заменяются присланными, чего нет в присланном — удаляется. `rz` — договоры всех ресурсов сразу: ресурс, которого нет в
  присланном `rz`, остаётся без договоров. Не присланный раздел не меняется.
- Поля `fl`, `t`, `area`, `inodn`, `del` пишутся, если присланы.
- `n`, если прислан, должен совпадать с номером в адресе.
- `_rev`, если прислан, должен совпадать с текущим отпечатком помещения. Иначе — 409 с `conflict: true`: помещение изменили
  после того, как клиент его загрузил (другое окно, импорт, корректировка, возврат копии). Исключение: последней это помещение
  записала та же вкладка (`X-Tab`), и отпечаток с тех пор не менялся — записи одной вкладки подряд не конфликтуют.
- `fio`, `prog`, `cno`, `cdt` помещения сервер вычисляет сам; присланные значения не записываются (`cdt` при этом
  проверяется на формат даты).
- Показания прибора: `prev`, `cur`, `midRead`, `ownRead` — за месяц `period` (`hist` за этот месяц не читается); других
  месяцев — в `hist`. Пишутся только присланные месяцы, остальные сохраняются; запись показаний удаляется только вместе с
  прибором.
- Не присланные `phones`, `emails`, `reps`, `rz` собственника берутся из прежней записи; так же `note`, `files`, `actDel`
  договора разграничения и `from`, `to` прибора.
- `prevSrc: "manual"` клиент присылает при ручной правке начального показания: такое начало не перезаписывают ни перенос
  «конец прошлого месяца», ни импорт.
- `lockPrev` и `lockCur` ставит только акт замены; клиент их не меняет.
- Номер прибора `id` сохраняется, пока у прибора те же ресурс и серийный номер. Новому прибору сервер даёт
  `помещение|ресурс|серийный номер` (при совпадении — `#2`, `#3`).
- Помещения с номером `n` нет — оно создаётся («помещение создано» в журнале).

Проверки до записи:

| Код | Отказ |
|---|---|
| 400 | тело пустое, массив или не объект; дата не `ГГГГ-ММ-ДД` или не существует (договор управления, владение, договор разграничения, акт опломбировки, установка и снятие прибора); показание не число; ресурс прибора не `hvs`, `gvs`, `ee`; программа не `none`, `hybrid`, `trust`, `share` |
| 409 | номер помещения в теле другой; отпечаток `_rev` устарел или помещение удалено (`conflict: true`); помещение из снимка закрытого месяца помечено на удаление; изменено показание, зафиксированное актом замены; изменена дата снятия прибора, снятого актом, или дата установки прибора, поставленного актом; прибор из акта замены помечен на удаление или удалён; у прибора с показаниями изменён серийный номер или ресурс (новый счётчик — только актом замены); удалён прибор, посчитанный в снимке закрытого месяца; вторая смена собственника в одном месяце |
| 500 | тело не JSON |

Что делает: пишет таблицы `units`, `programs`, `owners`, `meters`, `readings`, `contracts`; переносит ручные пометки
разграничения прежнего формата к собственнику; ставит начальные показания следующего месяца по конечным этого (кроме
внесённых вручную, корректировкой и актом); пишет журнал по изменённым полям.

Ответ 200 — пересобранное помещение (`Unit` за `period`) с новым `_rev`. Если месяц `period` закрыт, в ответе ещё
`closedPeriod: "ГГГГ-ММ"`: данные закрытого месяца изменены, снимок не тронут, разница оформляется корректировкой (3.13).

Пульт отправляет помещение целиком с `_rev`, полученным от сервера, и кладёт в строку только ответ на последнюю запись
помещения.

### 3.5. `DELETE /api/unit/:n`

Удаляет помещение со всем содержимым: собственники, договоры управления, приборы и все их показания, договоры разграничения,
акты замены. Перед удалением — копия базы `del-<n>`; журнал — «помещение удалено».

Ответ 200 — `{"ok": true}`. 409 — помещение есть в снимке закрытого месяца (или месяца, открытого заново). Существование
помещения не проверяется: несуществующий номер — тоже 200.

### 3.6. Помещение: порядок записи для клиента

1. Получить помещение (`GET /api/state` или `GET /api/unit/:n`) — вместе с `_rev`.
2. Отправить изменённое помещение с этим `_rev` и заголовком `X-Tab`.
3. Взять из ответа помещение и новый `_rev`.
4. На 409 с `conflict: true` — перечитать помещение и внести правку заново.

### 3.7. `POST /api/unit/:n/replace`

Акт замены прибора: старый прибор снимается датой акта с конечным показанием, новый ставится той же датой с начальным; оба
показания фиксируются и больше не меняются ни из формы, ни импортом. В месяце замены считаются оба прибора, со следующего
месяца — только новый.

Параметры: `period` — месяц, за который вернуть помещение в ответе (по умолчанию `settings.period`). Месяц акта — по его
дате.

Тело:

| Поле | Что |
|---|---|
| `oldId` | номер (`id`) снимаемого прибора этого помещения |
| `date` | дата замены, `ГГГГ-ММ-ДД` |
| `finalRead` | конечное показание старого прибора |
| `newSn` | серийный номер нового прибора |
| `initialRead` | начальное показание нового прибора |
| `newK` | коэффициент нового; пусто — как у старого |
| `note` | примечание |

Что делает:

- старый прибор: `to = date`, к примечанию — «снят <дата>, замена на <номер>»; показание месяца акта `cur = finalRead` с
  замком `lockCur`;
- новый прибор: `{id: "<помещение>|<ресурс>|<номер>", res как у старого, sn, k, from: date, bill: true}`, показание месяца
  акта `prev = initialRead` с замком `lockPrev`;
- ручная пометка разграничения старого электросчётчика переходит на новый;
- запись в `replacements`: `{id: "<помещение>|<ресурс>|<дата>|<старый номер>→<новый номер>", unit, res, date, period,
  old: {id, sn, final}, new: {id, sn, k, initial}, note, at}`;
- начало следующего месяца у нового прибора — конечное за месяц замены;
- журнал. Копия базы не делается.

Ответ 200 — помещение (`Unit` за `period`) с `_rev`.

Отказы — все с кодом 400: пустое тело; помещение или прибор не найдены; прибор уже снят или уже снят актом; нет даты,
конечного или начального показания, серийного номера нового прибора; такой серийный номер уже есть в помещении; дата акта —
в закрытом месяце или раньше последнего закрытого; конечное показание месяца уже зафиксировано другим актом; конечное
показание меньше начального показания месяца.

### 3.8. `GET /api/table/:name`

Таблица базы как хранится: `units`, `owners`, `meters`, `readings`, `contracts`, `tariffs`, `external`, `settings`, `log`
(весь журнал), `unit_names`, `closed_periods`, `adjustments`, `replacements`, `imports`, `programs`, `offsets`. Имя — латинские
буквы, цифры и «_». Таблицы нет — пустой список `[]`.

### 3.9. `PUT /api/table/:name`

Заменить справочник. Принимаются только `tariffs`, `external`, `settings`, `unit_names`; другие — 403 «таблица … не
редактируется целиком» (помещения, приборы, показания и договоры пишутся через `/api/unit`). Пустое тело — 400; тело не
JSON — 500.

| Таблица | Тело | Особенности | Ответ |
|---|---|---|---|
| `tariffs` | массив строк тарифа (2.4) | `base` и `vat`, присланные строкой («467,62»), приводятся к числу; журнал — по строкам (услуга + дата начала) | `{"ok": true}` |
| `external` | массив доходных контрагентов (2.3) | журнал не пишется | `{"ok": true}` |
| `unit_names` | объект `{номер: подпись}` | журнал не пишется | `{"ok": true}` |
| `settings` | объект настроек (2.3) | слиянием (ниже) | `{"ok": true, "settings": {…что записано}}` |

Настройки записываются слиянием:

- с полем `_base` — настройками, какими клиент их получил или записал в прошлый раз: берётся только то, что клиент изменил
  относительно `_base`; остальное остаётся, как на сервере. Ключ, удалённый клиентом, удаляется, только если на сервере его
  с тех пор не меняли. Вложенные объекты (`byPeriod` и др.) сливаются так же;
- без `_base` — заменяются целиком. Клиент обязан прислать всё, включая `byPeriod`, `heatByPeriod`, `users`, `audit`,
  `regSeen`, `regSeenRows`, иначе они пропадут;
- доходные месяца, заведённые клиентом автоматически (`extSrc` `copied` или `empty`), не заменяют список, уже записанный на
  сервере для этого месяца;
- журнал — переключатели, вводные и доходные месяца (1.6).

Пульт отправляет настройки по очереди: следующая запись уходит после ответа на предыдущую, `_base` берётся на момент
отправки.

Проверки содержания (тариф 0, пересекающиеся строки тарифа, вводные закрытого месяца, список пользователей) сервер стенда
не делает — `docs/ОТКРЫТЫЕ ВОПРОСЫ.md`, раздел 2.

### 3.10. `GET /api/period/:p`

Состояние месяца. Параметры: `full=1` — снимок целиком.

Ответ 200:

| Поле | Что |
|---|---|
| `period` | месяц |
| `closed` | заголовок снимка (2.5) без `units`, с числом помещений `unitCount`; с `full=1` — снимок целиком; месяц не закрыт — `null` |
| `closedPeriods`, `lastClosed` | закрытые месяцы; последний закрытый |
| `adjustments` | корректировки месяца |
| `carries` | корректировки с переносом в ОДН этого месяца |
| `credits`, `offsets` | как в `/api/state` |

Действия с месяцем (`/close`, `/reopen`, `/adjust/:n`) методом `GET` — 405 «нужен POST». `POST /api/period/:p` без действия —
404.

### 3.11. `POST /api/period/:p/close`

Закрыть месяц: расчёт фиксируется снимком; дальше месяц меняется только корректировками.

Тело:

| Поле | Что |
|---|---|
| `snapshot` | снимок месяца (2.5): `{period, engineVersion, checklist, inputs, ctx, totals, units, credits}`. Считает движок: `buildSnapshot(чек-лист)` |
| `force` | закрыть, хотя чек-лист не пройден |
| `note` | причина принудительного закрытия |
| `by` | кто |
| `revs` | `{номер помещения: _rev}` — отпечатки помещений, по которым считан снимок |

Проверки — все с кодом 409:

- месяц уже закрыт;
- закрывать по порядку: если закрытые месяцы есть, закрыть можно только месяц, следующий за последним закрытым;
- `snapshot.period` не равен `:p`; в снимке нет `inputs`, `ctx`, `units` или `totals`;
- в снимке нет какого-либо помещения (кроме помеченных на удаление);
- помещение изменилось после загрузки страницы (по `revs`);
- строки «Зачёт переплаты» в снимке не совпадают с зачётами месяца в базе;
- сумма квитанций помещения не равна начисленному по помещению (допуск — 0,05 ₸ на квитанцию); сумма по помещениям не равна
  `totals.accrued` (допуск — 0,01 ₸ на помещение);
- чек-лист не пройден (у пункта `ok: false`), а `force` нет; принудительное закрытие без `note`;
- тело не JSON.

Что делает: копия базы `close-<p>`; переносы корректировок прошлых месяцев, адресованные этому месяцу, дописываются в
доходные снимка (`inputs.external`, строки с `carryOf`); запись в `closed_periods` со статусом `closed`; переплаты
`credits` — только положительные, целыми тенге; журнал.

Ответ 200 — заголовок снимка (без `units`, с `unitCount`).

После закрытия:

- данные месяца в базе по-прежнему можно править (`PUT /api/unit` вернёт `closedPeriod`), снимок не меняется;
- импорт в закрытый месяц, зачёт в его квитанции, очистка месяца, акт замены с датой в нём — отказ;
- расчёт и выгрузка месяца — из снимка.

Баланс ОДН и тарифы сервер стенда при закрытии не пересчитывает: он доверяет отметкам чек-листа от страницы
(`docs/ОТКРЫТЫЕ ВОПРОСЫ.md`, раздел 2). Функция снимка в Node наружу не отдаётся (`createEngine()` её не возвращает):
закрывает месяц пульт.

### 3.12. `POST /api/period/:p/reopen`

Открыть закрытый месяц заново.

Тело: `{reason, by}`.

Проверки — все с кодом 409:

- месяц не закрыт;
- работающий — не «Руководитель» и не «Бухгалтерия» (`X-User`, иначе `by`);
- месяц — не последний закрытый;
- по месяцу есть корректировки (вместо открытия — отменяющая корректировка);
- нет причины;
- переплату этого месяца уже зачли в другом месяце или вернули деньгами, а другой переплаты собственника на это не хватает.

Что делает: копия базы `reopen-<p>`; статус снимка — `reopened` (снимок остаётся в базе), запись в `history`; журнал.
Повторное закрытие создаёт новую запись снимка.

Ответ 200 — `{"ok": true}`.

### 3.13. `POST /api/adjust-group/:n`

Оформить корректировку помещения `:n` — одно действие оператора по одному или нескольким закрытым месяцам.

- Последний закрытый месяц — полная корректировка (`scope: "full"`): каскад показаний в следующий месяц, документ за месяц.
- Более ранние месяцы — суммарные (`scope: "summary"`): без каскада.
- Переносы в ОДН и строки «Перерасчёт» — в первый открытый месяц, следующий за последним закрытым.

Расчёт «после» и документы готовит клиент движком в контексте снимка (в пульте — форма корректировки: `snapshotUnit`,
`acctDelta`, `correctiveInvFor`). Сервер проверяет, считает разницу и перенос, записывает. Изменённые реквизиты (показание,
договор, собственник) клиент записывает в помещение до этого запроса — `PUT /api/unit` за закрытый месяц.

Тело:

| Поле | Что |
|---|---|
| `cause` | причина полями (ниже) |
| `text` | пояснение. Печатается в квитанции, поэтому без ФИО. Для `other` обязательно — это и есть причина |
| `billing` | выбранный способ (`corrective` или `next-period`), для справки; способ записи определяется по документам |
| `by` | кто |
| `periods[]` | закрытые месяцы: `{period, after, invoices, seen, cascade}` |
| `changes` | правки помещения для справки (из журнала) |

Причина `cause`:

| `kind` | Поля | Тип корректировки |
|---|---|---|
| `contract` | `res` (`w`, `e`, `h`), `no`, `from`, `seal`, `sealNo` — договор разграничения | `contract` |
| `reading` | `meter` (подпись прибора), `meterId`, `period`, `field` (`prev` или `cur`), `was`, `now` | `reading`; при `now: null` — `reading-delete` |
| `owner` | `fio`, `date`, `ownRead` — смена собственника задним числом | `owner` |
| `amount` | `target` (`KU` или `EK`), `amount`, `key`, `fio`, `payer` — «сумма вручную» | `amount` |
| `other` | — | `other` |

Элемент `periods[]`:

| Поле | Что |
|---|---|
| `period` | закрытый месяц |
| `after` | расчёт помещения после корректировки в контексте снимка — в виде помещения снимка; `after.n` равно `:n` |
| `invoices[]` | документы корректировки (ниже) |
| `seen` | сколько корректировок помещения за этот месяц видел клиент. Не совпало с базой — отказ (повторное нажатие, другое окно) |
| `cascade` | только для показания в последнем закрытом месяце: `{mode, value}` — начальное следующего месяца: `auto` — новое конечное, `manual` — `value`, `empty` — пусто |

Корректировочная квитанция (способ А) — документ, который строит `correctiveInvFor` движка:

| Поле | Что |
|---|---|
| `kind` | `corrective` |
| `target` | `KU` или `EK` |
| `code` | `КВ-<помещение>-<месяц>/К?` или `ЭК-…/К?`; при нескольких квитанциях месяца — `/<номер части>К?`. Сервер заменяет `К?` на `К<seq>` |
| `replaces` | коды заменяемых квитанций |
| `part`, `parts` | номер части после корректировки (с 0; у аннулирующей — `null`), число частей |
| `fio`, `payer` | счёт квитанции: собственник и плательщик (`owner`, `uk`, `deduction`) |
| `from`, `to`, `days`, `share`, `area` | дни части, доля дней, площадь |
| `mgmt` | договор управления части: `{program, contractNo, contractDate, from}` или `null` |
| `lines` | строки части после корректировки — суммы и объёмы по услугам, строки по тарифам `tl`; у аннулирующей — `null` |
| `before` | строки заменяемой части, для справки |
| `manual` | «сумма вручную»: `[{name, amount}]` |
| `total` | сумма строк части |
| `was`, `now` | к оплате по счёту до и после, целые тенге, со знаком |
| `settle` | к доплате (+) или к зачёту деньгами (−), целые тенге |
| `creditDelta` | изменение переплаты по счёту |
| `annul` | `true` — аннулирующая: у счёта после корректировки квитанций нет (смена собственника или плательщика задним числом) |

Строка перерасчёта (способ Б): `{kind: "next-period", target, period: <первый открытый месяц>, fio, payer, ownFrom,
line: "Перерасчёт[ ЭК] за <месяц> — <причина>", amount}`. `amount` — разница к оплате по счёту, целые тенге.

Проверки — все с кодом 409:

- закрытых месяцев нет;
- тип причины не из списка; нет причины (для `other` — нет пояснения);
- нет месяцев; месяц не закрыт, позже последнего закрытого, помещения нет в его снимке;
- нет `after` или в нём другое помещение;
- показания (`reading`, `reading-delete`) правятся только в последнем закрытом месяце; в более раннем месяце показания в
  `after` отличаются от снимка;
- `seen` не совпал.

Тело не JSON — 500.

Что делает, по каждому месяцу:

- `seq` — следующий номер корректировки помещения за месяц; «до» — помещение снимка или «после» прошлой корректировки;
- разница `delta` — по строкам, частям и счетам «собственник + плательщик»;
- способ `billing` — по присланным документам: только корректировочные — `corrective`, только строки — `next-period`, оба
  вида — `mixed`, документов нет — `none`;
- полная корректировка — каскад: изменённое конечное показание закрытого месяца становится начальным следующего
  (`prevSrc: "adj:…"`; показание под замком акта не трогается);
- номера корректировочных: `К?` → `К<seq>`; совпали номера двух квитанций одного вида — `/1К<seq>`, `/2К<seq>` по порядку;
- перенос `carry` в ОДН первого открытого месяца — изменение объёма «в счёт УК» плюс изменение ОДН помещения, по воде,
  электроэнергии и теплу;
- переплата `credits` — по корректировочным квитанциям собственника: «к зачёту» деньгами плюс изменение минуса квитанции;
- журнал. Копия базы не делается.

Ответ 200 — `{"group": "ADJG-…", "adjustments": [записи корректировок (2.6)]}`.

После корректировки: месяц нельзя открыть заново; копии базы, сделанные до неё, не возвращаются; выгрузка закрытого месяца
содержит корректировочные квитанции (4.11); выгрузка первого открытого месяца — строки «Перерасчёт» (способ Б) и перенос в
ОДН.

### 3.14. `POST /api/period/:p/adjust/:n`

Прежний вариант — корректировка одного месяца, только последнего закрытого. Пульт его не использует.

Тело: `{type, reason или cause + text, billing, by, after, invoices, cascade, changes}`. Отличия от `adjust-group`: способ —
по сумме (разница меньше 0,005 ₸ — `none`, иначе `corrective` или `next-period` по `billing`); номера `К?` не заменяются;
переплата (`credits`) не считается; группы нет. Ошибки — 409. Ответ — запись корректировки.

### 3.15. `GET /api/adjustments`

| Параметры | Ответ |
|---|---|
| `period=ГГГГ-ММ`, `unit=N` (оба необязательны) | корректировки с отбором; без параметров — все |
| `carry=ГГГГ-ММ` | действующие корректировки с переносом в ОДН этого месяца |

### 3.16. Зачёт и возврат переплаты

`GET /api/offsets` — все записи `offsets` (2.7).

`POST /api/offsets` — зачесть переплату в квитанцию открытого месяца. Тело:

| Поле | Что |
|---|---|
| `unit` | помещение |
| `fio` | собственник — как в квитанции |
| `ownFrom` | с какой даты он владеет помещением (`null` — первый собственник): строка найдёт собственника и после исправления написания ФИО |
| `amount` | сумма, целые тенге больше нуля |
| `period` | открытый месяц `ГГГГ-ММ`, позже последнего закрытого |
| `type` | `KU` или `EK` — в какую квитанцию |
| `note` | пояснение, до 300 знаков; печатается в строке «Зачёт переплаты — …» |
| `seen` | сколько всего зачтено и возвращено по этому собственнику видел клиент; не совпало с базой — отказ |
| `by` | кто |

Возврат деньгами — тот же запрос с `type: "REFUND"`: `{unit, fio, amount, date, note, seen, by, type: "REFUND"}`. `date` —
не позже сегодняшнего дня по часам сервера; `note` — как вернули (перевод, наличные, номер платёжки), от 3 знаков; сумма — не
больше остатка переплаты по закрытым месяцам (начислено − зачтено − возвращено). Поля `period` у возврата нет.

Ответ 200 — созданная запись (2.7). Отказы — все с кодом 409: помещение не найдено; месяц не `ГГГГ-ММ` или закрыт; тип не
`KU` / `EK`; сумма не целая или не больше нуля; нет собственника; `seen` устарел; для возврата — нет даты, дата в будущем,
нет пояснения, сумма больше остатка. Тело не JSON — 500. Журнал: «зачёт переплаты · …», «переплата возвращена деньгами …».

Что сумма зачёта не больше остатка переплаты и не больше суммы квитанции, проверяет только окно пульта
(`docs/ОТКРЫТЫЕ ВОПРОСЫ.md`, раздел 2).

`DELETE /api/offsets/:id` — отменить. Зачёт — только пока его месяц открыт; возврат — в любой момент. Ответ —
`{"ok": true}`; 409 — записи нет или месяц закрыт. Журнал.

### 3.17. Импорт показаний

Файлы поставщиков кладутся как есть в папку проекта `Импорт/ГГГГ/ММ/` (папка проекта, а не папка базы): выгрузка АРЭК
(электроэнергия, снимок показаний на дату), отчёт Су-Арнасы (вода, начало и конец периода), ЭСФ Теплотранзита (тепло). Тип
файла определяется по содержимому (`server/parse_import.py`, Python 3 с `openpyxl` и `xlrd`).

`GET /api/import?period=ГГГГ-ММ` — предпросмотр, ничего не пишет. `POST /api/import?period=ГГГГ-ММ` — записать. `period` по
умолчанию — `settings.period`.

Ответ 200 (оба запроса):

| Поле | Что |
|---|---|
| `period`, `folder`, `exists` | месяц, папка, есть ли она |
| `files[]` | файлы: `{name, type, error, date, from, to, rows, gcal, regNo, docDate}`; `type` — `arek`, `water`, `esf`; не распознан — `error` |
| `items[]` | по прибору: `{meter, unit, res, sn, src, prev, cur, wasPrev, wasCur, skipPrev, skipCur, fileStart, fromStand, keep}` — что придёт и что было. `skipPrev` / `skipCur` — не перезаписывается; `keep` — почему: `act` — акт замены, `adj` — корректировка, `manual` — внесено вручную. `fileStart` — начало по файлу, если оно отличается от конца прошлого месяца в стенде |
| `unmatched[]` | приборы из файлов, которых нет в стенде: `{sn, unit, src}` |
| `missing[]` | приборы стенда без данных в файлах: `{meter, unit, res, sn, bill, why, keeps}` |
| `negative[]` | конец меньше начала: `{unit, res, sn, prev, cur}` |
| `stale[]` | модем Су-Арнасы молчит с начала периода: `{unit, res, sn, last, cur}` |
| `alerts[]` | что проверить до записи — текстом: файл не за тот месяц, одна ЭСФ дважды, нет начального показания электроэнергии и т. п. |
| `warnings[]` | прочие замечания — текстом |
| `heat` | тепло: `{gcal, files: [{name, supplier, docDate, issueDate, regNo, gcal, lines}]}` или `null` |
| `summary` | счётчики: `hvs`, `gvs`, `ee` — `{meters, prev, cur, locked, manual, adj, starts}`; `unmatched`, `missing`, `warnings`, `alerts`, `negative`, `stale` |
| `written`, `record` | только `POST`: сколько приборов изменено; запись протокола |

Правила сопоставления:

- прибор ищется по серийному номеру среди приборов своего ресурса; пробелы и ведущие нули не учитываются;
- помеченные на удаление и приборы вне месяца (сняты раньше, установлены позже) пропускаются;
- начало месяца — конец прошлого месяца в стенде; начало по файлу — только для сверки;
- показания акта замены, начало, внесённое вручную или поставленное корректировкой, не перезаписываются;
- электроэнергия: конец — по самому позднему снимку АРЭК в папке, начало — по самому раннему или по концу прошлого месяца.

`POST`: копия базы `pre-import-<ГГГГ-ММ>`; показания `prev` и `cur`; перенос начала следующего месяца; тепло —
`settings.heatByPeriod[месяц]` и позиции ЭСФ в `settings.byPeriod[месяц]` (`heat1`, `heatAmt`; при двух ценах в ЭСФ и двух
строках тарифа тепла — ещё `heat2`, `heat2Amt`); протокол в `imports`: `{period, at, folder, files, written, summary, heat,
unmatched, missing, warnings}`; журнал.

Ошибки: 409 — месяц закрыт (и для `GET`, и для `POST`); 400 — месяц не `ГГГГ-ММ`, Python не запустился, для `POST` — папки нет
или в ней нет данных. Папки нет — `GET` отвечает 200 с `exists: false`.

### 3.18. Вложения

`POST /api/files?name=<имя файла>` — принять файл. Тело — сам файл, не JSON; нужен заголовок `X-Tab` или `X-User`.

- Расширения: `.jpg`, `.jpeg`, `.png`, `.gif`, `.webp`, `.bmp`, `.tif`, `.tiff`, `.heic`, `.heif`, `.pdf`; другое — 415.
- Размер — до 25 МБ (иначе 413), не пустой (иначе 400).
- Файл сохраняется как `<база>/files/<ГГГГММДД-ччммсс-xxxxxx>.<расширение>` (местное время).
- Ответ 200: `{id, name, type, size, at, by}` — описание, которое клиент кладёт в `files[]` договора разграничения через
  `PUT /api/unit` (с `part`: `dog` — договор, `act` — акт). Без этого файл ни к чему не привязан.

`GET /api/files/:id` — отдать файл. Параметры: `name` — имя для сохранения; `dl=1` — скачать (`attachment`), иначе открыть
в браузере (`inline`). Ищется и среди убранных. Заголовок `Cache-Control: private, max-age=86400`. 404 — файла нет.

`DELETE /api/files/:id` — перенести файл в `<база>/files/_deleted`. Файл не стирается: возврат копии базы не останется без
сканов. 409 — файл ещё во вложениях договора. Ответ — `{"ok": true}`.

### 3.20. Очистка данных месяцев

Подготовка базы к загрузке настоящих месяцев: убирает данные выбранных месяцев, справочники остаются. Что удаляется и что
нет — `docs/ОЧИСТКА ДАННЫХ.md`.

`GET /api/clean-months` — месяцы, по которым есть данные, с числами: `{"periods": [счётчики]}`.

`GET /api/clean-months?periods=ГГГГ-ММ,ГГГГ-ММ` — предпросмотр по выбранным месяцам. 400 — месяцы не выбраны или не `ГГГГ-ММ`.

Счётчики месяца:

| Поле | Что |
|---|---|
| `period`, `label`, `closed` | месяц, словами, закрыт ли |
| `readings`, `readingsActKept` | записей показаний; из них останутся показания актов замены |
| `inputs`, `inputFields`, `heatImport` | есть ли вводные месяца (0 или 1), сколько полей заполнено, есть ли Гкал импорта ЭСФ (0 или 1) |
| `ext`, `carries`, `offsets`, `imports` | строк доходных месяца, переносов корректировок в ОДН месяца, зачётов в его квитанции, протоколов импорта |
| `nextCarriedStarts`, `nextManualStarts` | у следующего месяца, если его не очищают: начальных показаний, перенесённых из конца этого (пометка снимется), и внесённых вручную, корректировкой или актом (не трогаются) |

`POST /api/clean-months` — очистить. Тело: `{periods: ["ГГГГ-ММ", …], by}`. Проверки по порядку: 400 — месяцы не выбраны
или не `ГГГГ-ММ`; 403 — работающий (`X-User`, иначе `by`) не «Руководитель» и не «Бухгалтерия»; 409 — среди месяцев есть
закрытый (ничего не удаляется).

Удаляется за каждый месяц: показания (кроме зафиксированных актом замены); вводные месяца `settings.byPeriod[месяц]` и Гкал
ЭСФ `heatByPeriod[месяц]` (если очищается выбранный месяц — и их повтор в общих настройках); переносы корректировок в ОДН
месяца (объёмы обнуляются, прежние — в `carryCleared`); зачёты в квитанции месяца; протоколы импорта. У следующего месяца
перенесённые начала остаются числом без пометки. Перед удалением — копия базы, после — журнал.

Ответ 200: `{backup, by, periods: [счётчики до очистки], total: {readings, readingsActKept, inputs, ext, carries, offsets,
imports}}`.

### 3.21. Копии базы

`POST /api/backup?tag=<метка>` — сделать копию (1.7). Ответ — `{"dir": "<имя копии>"}`.

`GET /api/backups` — имена копий, новые сверху. С `info=1` — `[{dir, block, lack, after}]`: `block` — почему копию вернуть
нельзя (пустая строка — можно); `lack` — каких таблиц в копии нет; `after` — закрытия и корректировки, сделанные после копии:
`[{kind, period, unit, at}]`, `kind` — `close` или `adj`.

`POST /api/restore?dir=<имя копии>` — вернуть базу к копии.

| Код | Когда |
|---|---|
| 400 | не указан `dir` |
| 404 | копии нет |
| 409 | копия неполная (нет `units`, `owners`, `meters`, `readings`, `contracts`, `tariffs`, `settings` или `programs`); копия сделана раньше закрытия месяца или корректировки; файл копии не читается |

Что делает: текущее состояние — в копию `before-restore`; таблицы из копии заменяют текущие, таблица, которой в копии нет,
удаляется. Не возвращаются никогда `closed_periods`, `adjustments` и `log`: снимок закрытого месяца и корректировки
неприкосновенны, журнал — история. Отметки «просмотрено» (`settings.regSeen`, `regSeenRows`) остаются текущими. Память сервера
сбрасывается; журнал — «база возвращена к копии». Ответ 200 — `{"ok": true, "saved": "<имя копии before-restore>"}`.

Начала месяцев после возврата приводятся к концу прошлого месяца только при следующем запуске сервера.

### 3.23. Копия проекта на Google Диск

Работает, только если в проекте есть `tools/backup.js` (ноутбук стенда). Без него `GET /api/drive-backup` отвечает
`{"off": true}`, любой другой метод — 404 «копия на Google Диск в этой сборке не подключена»; пульт прячет кнопку.

`GET /api/drive-backup` — `{roots, last, busy}`: папки «Мой диск» подключённых Google Дисков; последняя копия на каждом —
`{root, file, count, at}`; идёт ли копирование.

`POST /api/drive-backup` — ZIP всей папки проекта (с `data/`, копиями базы, файлами поставщиков, историей правок; база из
`TORRE_DATA` вне папки проекта в архив не входит), проверка архива, запись в папку «TORRE копии» на каждом найденном Google
Диске; хранятся 10 последних. Занимает до 10 минут; другие запросы в это время обслуживаются. Ответ — 200 или 500
`{ok, out, last}` (`out` — текст вывода); 409 — копия уже делается. Журнал не пишется.

## 4. Выгрузка для личного кабинета (схема 1.6)

### 4.1. Откуда берётся

- Сервер: `GET /api/accruals?period=ГГГГ-ММ` (3.2).
- Пульт: «Отчёты» → «Квитанции за месяц» → «Для кабинета: JSON» — тот же документ с отступами; открытый месяц — после
  подтверждения, в имени файла «(черновик)». «Для кабинета: Excel» — то же содержание на трёх листах: «Документы»,
  «Строки», «Итоги».
- Node без сервера: `calcMonth(состояние, месяц).env` (раздел 5).

Документ строит `exportEnvelope()` движка: обычные квитанции — `invoiceDocs()`, корректировочные — `correctiveDocs()`, ноль с
причиной — `zeroReason()`, итоги документа — `payTotals()`.

Принципы:

- один документ — одна квитанция. Квитанция КУ (коммунальные услуги, код `КВ-…`) и квитанция ЭК (эксплуатационные расходы,
  код `ЭК-…`) — отдельные документы;
- ФИО в выгрузке нет: квитанция выставляется на помещение. Кто собственник в дни документа (`from` — `to`), кабинет
  определяет по своему реестру;
- числа — те же, что в квитанции стенда;
- `status: "open"` — черновик: суммы ещё могут измениться. Собственникам — после закрытия месяца (`status: "closed"`).

### 4.2. Конверт

| Поле | Тип | Что |
|---|---|---|
| `schemaVersion` | строка | `"1.6"` |
| `source` | строка | `"engine"` — расчёт стенда |
| `object` | строка | `"TOR'RE Astana"` |
| `period` | `ГГГГ-ММ` | расчётный месяц |
| `status` | строка | `open` — месяц не закрыт (черновик); `closed` — закрыт, документы из снимка |
| `generatedAt` | ISO | когда собран документ |
| `engineVersion` | строка | версия правил расчёта движка, которым собран документ. У закрытого месяца версия на момент закрытия — в снимке (`GET /api/period/:p`, поле `engineVersion`) |
| `rounding` | строка | правило округления словами |
| `totals` | объект | итоги (ниже) |
| `documents` | массив | документы (4.3) |

Итоги `totals`:

| Поле | Что |
|---|---|
| `units` | помещений в документах |
| `documents` | всего документов, включая корректировочные |
| `KU`, `EK` | `{count, sum, linesSum}` по обычным квитанциям (вместе с отдельными квитанциями прежнего собственника), без корректировочных: число документов, сумма `total`, сумма `linesTotal` |
| `byPayer` | `{company, deduction, owner}`, у каждого — `{KU, EK, documents}`: к оплате по обычным квитанциям плательщика и их число (КУ и ЭК вместе) |
| `corrective` | `{count, sum, difference}`: корректировочных документов (все, включая заменённые); к оплате по действующим (без `replacedBy`); сумма разниц всех корректировочных |
| `overpayment` | `{documents, sum}`: обычные квитанции с переплатой и сумма переплаты |

Сумма месяца не удваивается: корректировочные идут только в `totals.corrective`, в `KU`, `EK`, `byPayer` их нет.

### 4.3. Документ

| Поле | Тип | Что |
|---|---|---|
| `code` | строка | номер квитанции (4.4) |
| `type` | строка | `KU` или `EK` |
| `unit` | строка | номер помещения |
| `area` | число | площадь, м²; закрытый месяц — из снимка |
| `period` | `ГГГГ-ММ` | расчётный месяц |
| `from`, `to` | дата или `null` | дни документа включительно; `null` — отдельная квитанция прежнего собственника |
| `days` | число | дней в документе; 0 — отдельная квитанция прежнего собственника |
| `daysInMonth` | число | дней в месяце |
| `part`, `parts` | число | номер квитанции помещения в месяце (с 1) и сколько их; месяц не делится — 1 и 1 |
| `splitReason` | строка или `null` | почему документ отделён от предыдущего: `owner-change` — смена собственника, `program-change` — смена договора управления (плательщика) у того же собственника; `null` — месяц не делится или первая часть |
| `payer` | строка | кто платит: `company`, `deduction`, `owner` |
| `management` | объект или `null` | договор управления: `{program, contractNo, contractDate, from}`; `null` — не в управлении |
| `kind` | строка | вид квитанции — подпись, не для логики. Есть у КУ, у отдельной и у корректировочной; у обычной ЭК поля нет |
| `corrective` | объект | только у корректировочной (4.11) |
| `issueMonth` | `ГГГГ-ММ` | только КУ: месяц выставления — следующий за расчётным |
| `issueDate` | дата | только ЭК: дата выставления — 25-е число расчётного месяца; у корректировочной ЭК — день оформления корректировки по часам сервера |
| `dueDate` | дата | только ЭК: оплатить до 10-го числа следующего месяца; у корректировочной ЭК поля нет |
| `lines` | массив | строки (4.5) |
| `linesTotal` | число | сумма строк, до копейки |
| `total` | число | к оплате, целые тенге, не меньше 0 |
| `rounding` | число | округление (4.9) |
| `overpayment` | число | только если сумма строк в минусе: переплата, целые тенге |
| `negativeUsage` | массив | только у КУ, если есть прибор с отрицательным расходом (4.8) |

Плательщик `payer`:

| Значение | Что |
|---|---|
| `company` | платит УК: помещение в управлении по гибридной или доверительной программе, переключатель «компания платит КУ за помещения в управлении» включён |
| `deduction` | долевая программа: УК оплачивает и удерживает из доли собственника |
| `owner` | платит собственник |

`company` и `deduction` — помещения в управлении: их суммы берёт отчёт собственнику; `owner` — квитанция к оплате
собственником.

Договор управления `management` — действующий в первый день документа (закрытый месяц — из снимка): `program` — `hybrid`
(гибридная), `trust` (доверительная), `share` (долевая); `contractNo`, `contractDate` — номер и дата договора; `from` — в
управлении с.

Вид квитанции `kind`:

| Значение | Когда |
|---|---|
| `УК полностью` | разграничения нет: все ресурсы — в счёт УК |
| `УК только с ОДН` | все ресурсы у поставщика по разграничению: в квитанции только ОДН |
| `УК: ОДН + <ресурсы>` | часть ресурсов в счёт УК: «вода», «электро», «тепло», с пометкой «(частично)»; в месяце продажи — «доля счёта поставщика (…)» |
| `отдельная — только строки прежнего собственника` | 4.10 |
| `корректировочная` | 4.11 |

Порядок документов: по помещениям в порядке таблицы помещений; внутри помещения — отдельные квитанции прежнего собственника,
затем части месяца по датам, у каждой — КУ, потом ЭК; корректировочные — в конце массива.

### 4.4. Коды документов

| Документ | Код |
|---|---|
| КУ за месяц | `КВ-5017-2026-06` |
| ЭК за месяц | `ЭК-5017-2026-06` |
| несколько квитанций в месяце | `КВ-1709-2026-06/1`, `КВ-1709-2026-06/2` — по порядку; отдельные квитанции прежнего собственника — первыми |
| корректировочная | `КВ-5017-2026-06/К1`; при нескольких квитанциях в месяце — `/2К1`. `К<n>` — номер корректировки помещения за месяц. Совпали номера двух документов одного вида в одной корректировке — `/1К<n>`, `/2К<n>` по порядку |

Код уникален в выгрузке месяца; повторная выгрузка того же месяца даёт те же коды.

### 4.5. Строка

| Поле | Тип | Что |
|---|---|---|
| `code` | строка | код строки (ниже) |
| `name` | строка | название, как в квитанции |
| `unit` | строка или `null` | единица: `м3`, `кВт·ч`, `Гкал`, `м2`; у строк `recalc`, `offset`, `manual` — `null` |
| `volume` | число или `null` | объём; у ЭК — площадь, м² |
| `share` | число | только ЭК: доля дней документа (дни ÷ дни месяца) |
| `tariff` | число или `null` | тариф с НДС, ₸ за единицу; у строк КУ — до 4 знаков |
| `amount` | число | сумма, ₸, до копейки |
| `from`, `to` | дата | только если тариф менялся в днях документа: дни этого тарифа |
| `zero` | объект | ноль с причиной (4.6) |
| `supplierShare` | объект | доля счёта поставщика (4.7) |

Коды строк:

| `code` | `name` | Ед. | Что |
|---|---|---|---|
| `water_supply` | Водоснабжение | м3 | вода (ХВС и ГВС) в счёт УК за дни документа; `zero`, `supplierShare` |
| `water_drainage` | Водоотведение | м3 | тот же объём воды; `zero`, `supplierShare` |
| `odn_water_supply` | ОДН водоснабжение | м3 | ОДН воды на помещение × доля дней |
| `odn_water_drainage` | ОДН водоотведение | м3 | то же |
| `electricity` | Электроэнергия | кВт·ч | электроэнергия в счёт УК; `zero`, `supplierShare` |
| `odn_electricity` | ОДН электроэнергия | кВт·ч | ОДН электроэнергии на м² × площадь × доля дней |
| `heat` | Теплоэнергия | Гкал | коэффициент отопления × площадь × дни ÷ дни месяца — у неразграниченных по теплу; `zero`, `supplierShare` |
| `odn_heat` | ОДН теплоэнергия | Гкал | ОДН тепла на м² × площадь × доля дней |
| `maintenance` | Техническое обслуживание МОП (м2) | м2 | ЭК: площадь × тариф × доля дней |
| `capital_repair` | Взносы на капитальный ремонт | м2 | ЭК: то же |
| `recalc` | Перерасчёт[ ЭК] за <месяц или месяцы> — <причина> | — | перерасчёт закрытого месяца способом Б; ± целые тенге; в КУ или ЭК |
| `offset` | Зачёт переплаты[ — пояснение] | — | зачёт переплаты; минус, целые тенге; в КУ или ЭК |
| `manual` | Корректировка суммы[ — пояснение] | — | только в корректировочной: «сумма вручную» |

Порядок строк. КУ — восемь услуг в порядке таблицы, затем `recalc`, затем `offset`; в корректировочной после услуг —
`manual`, затем `recalc` и `offset`. ЭК — `maintenance`, `capital_repair`, затем `recalc`, `offset`. В отдельной квитанции
прежнего собственника — только `recalc` и `offset`. Число строк не постоянно.

Тариф менялся в днях документа (с 1.5). Строка услуги повторяется на каждый тариф с полями `from` и `to` (дни этого тарифа,
включительно): объём своих дней, свой тариф; строки одной услуги — подряд, по датам. Один тариф на все дни документа — одна
строка без `from` и `to` с тарифом этих дней. Так же — строки ОДН воды и электроэнергии, `maintenance` и `capital_repair`
(`share` — доля дней своего тарифа). Тепло (`heat`, `odn_heat`) — всегда одной строкой по тарифу тепла месяца: при смене
тарифа внутри месяца — средний по Гкал двух позиций ЭСФ Теплотранзита. Строка услуги КУ с суммой 0 — всегда одна, тариф —
последних дней документа.

Объём и сумма. `amount` = `volume × tariff` (у ЭК — `volume × share × tariff`), вверх до копейки. Объём выдаётся с таким
числом знаков, при котором это равенство выполняется на калькуляторе: вода, ОДН воды и ОДН электроэнергии — от 3 знаков,
электроэнергия — от 2, тепло и ОДН тепла — от 4, доля дней ЭК `share` — от 4; не больше 8. Если подобрать нельзя (сумма строки
сложена из нескольких округлённых частей, например вместе с долей счёта поставщика), — минимальное число знаков.

ОДН при компенсации «ЭК берёт из ОДН» (с 1.4): объём строк ОДН — уже с коэффициентом компенсации, `amount` — от него.
Собственник компенсацию не видит.

### 4.6. Ноль с причиной (`zero`)

Строка услуги (`water_supply`, `water_drainage`, `electricity`, `heat`) с суммой 0, если её объём за дни документа ушёл
поставщику напрямую (разграничение) или «спит» (счёт поставщика оплачивает УК). Обычный ноль — потребления не было — без
`zero`. У строк ОДН причины не бывает: ОДН начисляется всем.

| Поле | Что |
|---|---|
| `reason` | `direct` — собственник платит поставщику напрямую; `supplier_paid_by_company` — «спит»: помещение в управлении, счёт поставщика оплачивает УК; `supplier_paid_from_share` — «спит» в долевой программе: счёт оплачивает УК и удерживает из доли собственника |
| `supplier` | `Су-Арнасы` — вода, `АРЭК` — электроэнергия, `Теплотранзит` — тепло |
| `contractNo` | номер договора разграничения или `null` |
| `contractDate` | дата договора (по воде — дата самого договора, не акта) или `null` |
| `effectiveFrom` | с какой даты действует разграничение: вода — дата акта опломбировки; электроэнергия и тепло — дата договора; `null` — даты нет |
| `byFact` | договор «по факту» — без номера или без даты |
| `manual` | разграничено ручной пометкой собственника без договора; номер и даты — `null` |
| `actNo`, `actDate` | только вода: номер и дата акта опломбировки |

Пример подписи в кабинете: «Водоснабжение — 0,00 ₸: по договору разграничения № 35986 от 05.08.2025 (акт опломбировки от
20.11.2025) собственник платит Су-Арнасы напрямую».

### 4.7. Доля счёта поставщика (`supplierShare`)

Месяц продажи помещения, разграниченного договором прежнего собственника. Поставщик выставил счёт за весь месяц по договору
прежнего; объём за дни нового собственника выставляется новому через УК. Строка услуги (`water_supply`, `water_drainage`,
`electricity`, `heat`; при строках по тарифам — первая строка услуги) в документе нового собственника несёт:

| Поле | Что |
|---|---|
| `reason` | `previous_owner_contract` |
| `supplier` | поставщик |
| `contractNo`, `contractDate` | договор разграничения прежнего собственника |
| `days`, `daysInMonth` | дни документа, дни месяца |
| `volume` | объём доли (вода — 3 знака, электроэнергия — 2, тепло — 4); входит в объём строки |
| `note` | пояснение |

Сумма доли считается по тарифу, как у обычной строки, и входит в `amount`, `linesTotal`, `total`. В базу ОДН и в
счёт-фактуру УК этот объём не входит. У прежнего собственника строка той же услуги — нулевая с `zero.reason: "direct"`.

### 4.8. Отрицательный расход (`negativeUsage`)

С 1.6. У документов КУ помещения (у всех частей месяца), если у прибора, участвующего в расчётах, конечное показание месяца
меньше начального: расход прибора обнулён, разница ушла в ОДН дома.

```json
"negativeUsage": [ { "resource": "water", "meter": "8481013", "prev": 175.816, "cur": 174.798 } ]
```

`resource` — `water` или `electricity`, `meter` — серийный номер прибора. В квитанции собственника это не печатается;
кабинет может показать пометку. У корректировочных и отдельных квитанций поля нет.

### 4.9. Округление и итоги документа

1. Сумма каждой строки — вверх до копейки. Промежуточные расчёты не округляются; тариф с НДС не округляется (в строке КУ
   выдаётся до 4 знаков).
2. `linesTotal` — сумма строк, до копейки.
3. `total` — к оплате: `linesTotal` вверх до целого тенге, не меньше 0.
4. Сумма строк в минусе (перерасчёт или зачёт больше начисления): `total` = 0, `overpayment` — переплата целыми тенге по
   правилам математики: 0,50 и больше — вверх.
5. `rounding` — только округление: `total − overpayment = linesTotal + rounding` (без поля `overpayment` — 0).

| `linesTotal` | `total` | `rounding` | `overpayment` |
|---|---|---|---|
| 39 022,83 | 39 023 | 0,17 | — |
| 0,00 | 0 | 0 | — |
| −613,75 | 0 | −0,25 | 614 |
| −613,40 | 0 | 0,40 | 613 |

Строки `recalc` и `offset` — целые тенге.

### 4.10. Части месяца. Отдельная квитанция прежнего собственника

Месяц помещения делится на части — подряд идущие дни с одним собственником и одним плательщиком (смена собственника, вход в
управление или выход из него). Каждая часть — своя пара документов КУ и ЭК со своими `from`, `to`, `days`, `part`, `parts`,
`splitReason`, `payer`, `management`. Объёмы приборов делятся по показанию на дату передачи, без него — по дням; ОДН и ЭК —
по доле дней.

Пример — помещение 1709, июнь 2026: с 9 июня оно в доверительной программе, платит УК.

| `code` | Дни | `days` | `part` / `parts` | `splitReason` | `payer` | `management.program` | `linesTotal` | `total` |
|---|---|---|---|---|---|---|---|---|
| `КВ-1709-2026-06/1` | 01.06–08.06 | 8 | 1 / 2 | `null` | `owner` | `null` | 1 991,10 | 1 992 |
| `ЭК-1709-2026-06/1` | 01.06–08.06 | 8 | 1 / 2 | `null` | `owner` | `null` | 5 433,98 | 5 434 |
| `КВ-1709-2026-06/2` | 09.06–30.06 | 22 | 2 / 2 | `program-change` | `company` | `trust` | 5 475,46 | 5 476 |
| `ЭК-1709-2026-06/2` | 09.06–30.06 | 22 | 2 / 2 | `program-change` | `company` | `trust` | 14 943,44 | 14 944 |

Отдельная квитанция прежнего собственника. Строку «Перерасчёт за …» или «Зачёт переплаты» выставили собственнику, у которого
в этом месяце нет ни дня владения (собственник сменился с 1-го числа). Ему — отдельный документ месяца только с этими
строками:

- код `КВ-<помещение>-<месяц>/1` (КУ); ЭК — `ЭК-…/1`, только если есть строка ЭК;
- `kind`: «отдельная — только строки прежнего собственника»;
- `from`, `to` — `null`, `days` — 0, `splitReason` — `owner-change`, `management` — `null`, `payer` — как у строки;
- итоги и переплата — как у любого документа.

Документы за дни месяца идут после него: `/2`, `/3`…; при одной части — с `splitReason: "owner-change"`. После закрытия
месяца документ тот же: снимок хранит у строки пометку `sep`.

### 4.11. Корректировочные квитанции

Есть только в выгрузке закрытого месяца, если по нему оформлены корректировки способом А (`billing` `corrective` или
`mixed`). Способ Б корректировочных документов не даёт: разница — строкой `recalc` в обычной квитанции первого открытого
месяца.

Корректировочная — полный документ, как обычный, со своими строками:

| Поле | Что |
|---|---|
| `code` | `…/К<n>` (4.4) |
| `kind` | `корректировочная` |
| `payer`, `management`, `part`, `parts`, `from`, `to`, `days`, `area` | свои: при смене собственника или плательщика задним числом — новые |
| `splitReason` | как у заменённой |
| `issueMonth` (КУ) | следующий месяц за расчётным |
| `issueDate` (ЭК) | день оформления корректировки; `dueDate` нет |
| `lines` | строки заново: объёмы после корректировки, тарифы снимка месяца; строки `manual`; строки `recalc` и `offset` заменяемой квитанции этого счёта |
| `linesTotal`, `total`, `rounding`, `overpayment` | как у любого документа |
| `corrective` | что заменяет и разница (ниже) |

Поле `corrective`:

| Поле | Что |
|---|---|
| `replaces` | коды заменяемых документов. Первая корректировка — исходные квитанции счёта (у новой квитанции другому собственнику или плательщику — `[]`); следующие — предыдущая корректировочная того же помещения, счёта и вида |
| `original` | коды исходных квитанций |
| `replacedBy` | только у заменённой корректировочной: код той, что её заменила |
| `annul` | `true` — аннулирующая: после корректировки у счёта квитанций нет (смена собственника или плательщика задним числом); строки нулевые, у ЭК доля 0 |
| `adjustment`, `group` | номер корректировки `ADJ-…` и группы `ADJG-…` |
| `issuedAt` | когда оформлена, ISO |
| `reason` | причина без ФИО: «показание Электро 306386: 2 276,14 → 2 286,14», «смена собственника с 15.06.2026», «разграничение по воде, договор №… с …, акт …» |
| `replacedTotal` | к оплате по заменённому, не меньше 0 |
| `difference` | к доплате (+) или к возврату (зачёту) деньгами (−), целые тенге |
| `overpaymentChange` | на сколько изменилась переплата по квитанции счёта |

Разница считается по счёту квитанции «собственник + плательщик»: при доверительной программе задним числом собственнику —
к зачёту, УК — к доплате. Если у счёта после корректировки несколько документов (несколько частей), `difference` и
`replacedTotal` — у первого, у остальных 0.

### 4.12. Как обрабатывать выгрузку

1. Ключ документа — `code`. Повторная выгрузка месяца заменяет документы по коду.
2. Корректировочная заменяет документы из `corrective.replaces`: показывать её, заменённые хранить историей. Действующая —
   та, у которой нет `replacedBy`. `difference` больше нуля — к доплате, меньше — к возврату.
3. Отбор по `payer`: `company` и `deduction` — в отчёт собственнику помещения в управлении; `owner` — квитанция к оплате
   собственником.
4. Проверка на входе: сумма `amount` строк равна `linesTotal`; `total` — `linesTotal` вверх до целого, не меньше 0; итоги
   конверта равны суммам документов. Не сходится — записать в журнал, документ показать.
5. Не рассчитывать на постоянное число строк и полей. Необязательные поля: `zero`, `supplierShare`, `from` и `to` у строки,
   `share` (только ЭК), `kind` (нет у обычной ЭК), `corrective`, `overpayment`, `negativeUsage`, `dueDate` (нет у
   корректировочной ЭК). Неизвестные поля пропускать.
6. Строку с `from` и `to` подписывать датами: «Водоснабжение (01.08.2026–15.08.2026)».
7. Ноль с `zero` — показывать причину рядом со строкой; ноль без `zero` — обычный ноль, без пояснения.
8. Публиковать собственникам — месяц со `status: "closed"`.

Известные ошибки, которые затрагивают выгрузку (например, корректировочные при двух квитанциях одного счёта в месяце), —
`docs/ОТКРЫТЫЕ ВОПРОСЫ.md`, раздел 3.

## 5. Расчёт без сервера

Движок — один файл `engine/calc.js` для пульта и сервера; других копий формул нет. В Node:

```js
const { calcMonth, createEngine } = require('./engine/calc.js');

// state — данные месяца: ответ GET /api/state?period=2026-06
const r = calcMonth(JSON.parse(JSON.stringify(state)), '2026-06');
if (r.errs.length) throw new Error(r.errs.join('\n'));

r.env;       // документ выгрузки — раздел 4 (то же, что GET /api/accruals)
r.units;     // по помещениям: { '5017': { KU: [39022.83], EK: [20230.8], payer: 'owner' } }
r.balance;   // баланс ОДН дома: вода, электроэнергия, тепло, компенсация «ЭК берёт из ОДН»
r.ctx;       // коэффициенты: odnPerUnitW, odnPerAreaE, kOt, kOdn, ekFactor, nOdn, areaOdn, heatBaseArea, heatRest
```

- Вход — ровно ответ `GET /api/state` за месяц. На сервере его собирает `server/accruals.js` (`stateOf`: `db.getState(месяц)` и
  `periods.info(месяц, true)`). Закрытый месяц (`state.closed`) считается из снимка, с корректировочными квитанциями.
- Каждый вызов `calcMonth` идёт в новом контексте движка; расчёты не мешают друг другу. Движок может дописывать поля в
  переданные объекты — передавайте копию.
- `r.errs` не пуст — в `r.env` нет документов помещений с ошибкой; такой документ не использовать (сервер в этом случае
  отвечает 500 и документ не выдаёт).
- `r.units[n].KU` и `.EK` — суммы строк расчёта по частям месяца (без строк перерасчёта и зачёта); `payer` — внутренние
  значения движка: `owner`, `uk`, `deduction`, `mixed` (в выгрузке `uk` — это `company`).
- `createEngine()` — новый контекст с отдельными формулами: `payRound`, `payTotals`, `round2`, `ceil2`, `acctKey`, `acctMap`,
  `acctDelta`, `fieldDelta`, `deltaAny`, `carryFromDelta`, `monthInputs`, а также `ENGINE_VERSION` и `EXPORT_SCHEMA`.
- В браузере: `<script src="/engine/calc.js"></script>` — функции движка глобальные, данные месяца и поля ввода даёт пульт.
  Снимок закрытия (`buildSnapshot`) и документы корректировки (`snapshotUnit`, `correctiveInvFor`) сейчас доступны только так.
- Проверка: `npm run check` считает июнь 2026 тестового набора (`tests/fixtures/2026-06`) и сверяет с `tests/etalon.json`;
  ожидаемый результат — «Расхождений: 0».

Вход и выход движка, порядок расчёта месяца — `engine/README.md`; правила расчёта — `docs/ПРАВИЛА РАСЧЁТА.md`.
