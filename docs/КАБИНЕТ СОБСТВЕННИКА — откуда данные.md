# Кабинет собственника — откуда брать данные

Для разработчика кабинета. Состояние на 06.10.2026, выгрузка квитанций — схема 1.6.

Ниже — какие экраны у кабинета собственника, что на каждом показать и из какого поля выгрузки или
таблицы это взять. Как считаются суммы, здесь не описано: кабинет расчёт не повторяет.

## 1. Коротко

- **Суммы считает стенд, кабинет только показывает.** Кабинет ничего не пересчитывает: не умножает объём на тариф, не
  округляет, не решает, кто платит, не делит месяц на части. Если `total` не сходится с суммой строк, это ошибка данных:
  записать в журнал, а квитанцию показать как пришла.
- **Данные приходят из двух мест.**
  - **(а) Выгрузка квитанций за закрытый месяц.** Это JSON-файл по схеме 1.6, сейчас основной путь. Делается в стенде:
    отчёт «Квитанции за месяц» → «Для кабинета: JSON». Excel — запасной вариант с тем же содержанием (три листа:
    «Документы», «Строки», «Итоги»). Один документ — одна квитанция. С 05.10.2026 тот же документ за весь месяц отдаёт и
    сервер стенда: `GET /api/accruals?period=ГГГГ-ММ` (раздел 6).
  - **(б) Справочники стенда** — таблицы `data/*.json`: помещения, собственники, договоры, приборы, показания, закрытые
    месяцы, корректировки, зачёты. В продакшене это те же таблицы в БД, поля называются так же (`docs/СХЕМА ДАННЫХ.md`).
- **Квитанция выставлена на помещение, а не на человека.** ФИО в выгрузке нет. Чья квитанция, определяется по таблице
  собственников `owners` на даты документа (`from`–`to`).
- Полное описание выгрузки — `docs/API.md`, раздел 4. Кодов `direct-contract`, `sleeping-contract`, `transit`, запроса
  `GET /api/export`, полей `justification`, `owner.fio`, `revision` в выгрузке нет — это ранний проект, он не сделан.

### Что откуда — в целом

| Экран кабинета | Откуда в основном |
|---|---|
| 3.1 Мои помещения | таблица `units` |
| 3.2 Собственник и срок владения | таблица `owners` |
| 3.3 Договор управления, кто платит | таблица `programs`; кто платит — выгрузка, `payer` |
| 3.4 Договоры разграничения с поставщиками | таблица `contracts`; в квитанции месяца — выгрузка, `zero` и `supplierShare` |
| 3.5 Квитанции месяца — КУ и ЭК | выгрузка |
| 3.6 Перерасчёт за прошлые месяцы | выгрузка, строка `recalc` |
| 3.7 Корректировочные квитанции | выгрузка, поле `corrective` |
| 3.8 Зачёт переплаты | выгрузка, строка `offset` |

## 2. Выгрузка — поля, которые нужны кабинету

Код выгрузки — `exportEnvelope`, `invoiceDocs`, `correctiveDocs`, `EXPORT_SCHEMA` в движке `engine/calc.js`. Проверка движка —
`npm run check`.

### Конверт (файл целиком)

| Поле | Что это |
|---|---|
| `schemaVersion` | версия формата, сейчас «1.6» (с 06.10.2026: признак отрицательного расхода `negativeUsage`, переплата — до целого тенге по правилам математики; 1.5 — строка услуги на каждый тариф, см. «Строка на каждый тариф») |
| `source`, `object` | `engine` (расчёт стенда), «TOR'RE Astana» |
| `period` | месяц, ГГГГ-ММ |
| `status` | `closed` — месяц закрыт, можно показывать. `open` — черновик (в имени файла «(черновик)»): суммы ещё могут поменяться |
| `generatedAt` | когда выгружено (ISO) |
| `engineVersion` | версия правил расчёта, строкой — для журнала |
| `rounding` | правило «к оплате» текстом |
| `totals` | итоги для проверки при приёме: `units`, `documents`; `KU` и `EK` — `count`, `sum` (к оплате), `linesSum`; `byPayer` — по плательщикам; `corrective` — корректировочные (`count`, `sum`, `difference`); `overpayment` — переплата (`documents`, `sum`) |
| `documents` | квитанции — массив документов |

В `totals.KU`, `totals.EK`, `totals.byPayer` входят только обычные квитанции. Корректировочные считаются отдельно, в
`totals.corrective`, чтобы сумма месяца не удвоилась.

### Документ — одна квитанция

| Поле | Что это |
|---|---|
| `code` | номер квитанции: `КВ-5017-2026-06` — коммунальная, `ЭК-5017-2026-06` — эксплуатационная. Если месяц поделён — `/1`, `/2`. Корректировочная — `/К1`, `/К2` (если месяц поделён — `/1К1`, `/2К1`; смена собственника или плательщика с 1-го числа — аннулирующая прежнему `/1К1`, новая другому `/2К1`). Номер уникален внутри выгрузки |
| `type` | `KU` — коммунальная (КУ), `EK` — эксплуатационная (ЭК) |
| `unit` | номер помещения: «5017», «НП1», «2.004» |
| `area` | площадь, м². Для закрытого месяца берётся из снимка этого месяца, а не из сегодняшних данных |
| `period`, `from`, `to`, `days`, `daysInMonth` | месяц, даты квитанции (ГГГГ-ММ-ДД, включительно), дней в квитанции и в месяце |
| `part`, `parts` | номер части и сколько всего частей; если месяц не поделён — 1 из 1 |
| `splitReason` | почему поделён: `owner-change` — смена собственника, `program-change` — вход в управление, выход из него или смена программы. У первой части `null` |
| `payer` | кто платит: `owner` — собственник, `company` — платит УК, `deduction` — из доли собственника. Есть у каждого документа; других значений не бывает |
| `management` | договор управления на даты квитанции: `program` (`hybrid` — гибридная, `trust` — доверительная, `share` — долевая), `contractNo`, `contractDate`, `from`. Если `null` — помещение не в управлении |
| `kind` | у КУ — вид квитанции: «УК полностью», «УК только с ОДН», «УК: ОДН + вода, электро…». У корректировочной (КУ и ЭК) — «корректировочная». У обычной ЭК поля нет |
| `issueMonth` | только у КУ: месяц выставления (следующий за `period`) |
| `issueDate`, `dueDate` | только у ЭК: дата выставления (25-е число месяца) и срок оплаты (10-е число следующего месяца). У корректировочной ЭК `issueDate` — дата корректировки |
| `lines` | строки квитанции |
| `linesTotal` | итог по строкам, до копейки (это сумма `amount` всех строк) |
| `total` | к оплате: целые тенге, не меньше 0 |
| `rounding` | округление до целого тенге |
| `overpayment` | есть, только если сумма строк ушла в минус. Тогда это переплата в целых тенге (до целого по правилам математики: 0,50 и больше — вверх, −613,75 → 614), а `total` равен 0 |
| `corrective` | есть только у корректировочной (см. 3.7) |
| `negativeUsage` | только у КУ, со схемы 1.6: у прибора конечное показание месяца меньше начального, расход обнулён — список `{resource, meter, prev, cur}` (`resource`: `water` / `electricity`). В квитанции собственника это не печатается; как показывать собственнику — открытый вопрос (`docs/ОТКРЫТЫЕ ВОПРОСЫ.md`, В4) |

### Строка

| Поле | Что это |
|---|---|
| `code` | услуга (таблица ниже) |
| `name` | название ровно как в квитанции стенда — показывать без изменений |
| `unit` | единица: «м3», «кВт·ч», «Гкал», «м2». У перерасчёта, зачёта и корректировки суммы — `null` |
| `volume` | объём; у ЭК — площадь |
| `share` | только у ЭК: доля дней (1 — весь месяц). У строки с `from`/`to` — доля дней этого тарифа |
| `tariff` | тариф с НДС, до 4 знаков |
| `from`, `to` | со схемы 1.5: есть, только если тариф услуги менялся в днях квитанции — дни, когда действовал тариф этой строки (ГГГГ-ММ-ДД, включительно). Нет полей — строка за все дни квитанции |
| `factor` | до схемы 1.4 — у строк ОДН при компенсации ОДН (коэффициент). С 1.4 его нет: объём строки ОДН уже с компенсацией, строка = `volume × tariff` |
| `amount` | сумма строки до копейки |
| `zero` | ноль с причиной (см. 3.4) |
| `supplierShare` | доля счёта поставщика в месяц продажи (см. 3.4) |

| `code` | Где | `name` |
|---|---|---|
| `water_supply` | КУ | Водоснабжение |
| `water_drainage` | КУ | Водоотведение |
| `odn_water_supply` | КУ | ОДН водоснабжение |
| `odn_water_drainage` | КУ | ОДН водоотведение |
| `electricity` | КУ | Электроэнергия |
| `odn_electricity` | КУ | ОДН электроэнергия |
| `heat` | КУ | Теплоэнергия |
| `odn_heat` | КУ | ОДН теплоэнергия |
| `maintenance` | ЭК | Техническое обслуживание МОП (м2) |
| `capital_repair` | ЭК | Взносы на капитальный ремонт |
| `recalc` | КУ и ЭК | «Перерасчёт за … — причина» / «Перерасчёт ЭК за … — причина» (см. 3.6) |
| `offset` | КУ и ЭК | «Зачёт переплаты» или «Зачёт переплаты — примечание» (см. 3.8) |
| `manual` | только корректировочная | «Корректировка суммы» или «Корректировка суммы — пояснение» (см. 3.7) |

В КУ — восемь услуг, в ЭК — две, всегда в этом порядке, даже если сумма строки 0. Обычно это восемь и две строки; если
тариф услуги менялся в днях квитанции, строка этой услуги повторяется (ниже). Строки `recalc`, `offset`, `manual` идут
после строк услуг.

Число знаков в объёме и в доле дней подобрано так, чтобы `volume × tariff` (× `share`), округлённое вверх до
копейки, дало ровно `amount`. Показывать числа как есть: если обрезать до двух знаков, у собственника не сойдётся на
калькуляторе.

### Строка на каждый тариф (схема 1.5, с 05.10.2026)

Если тариф услуги менялся в днях квитанции (например, водоснабжение подорожало с 16-го), в квитанции по этой услуге не одна
строка, а **по строке на каждый тариф**: объём квитанции поделён между тарифами по дням, у каждой строки — объём своих дней,
свой тариф, своя сумма и поля `from`, `to`. Так решил заказчик (04.10.2026).

| Что | Как |
|---|---|
| Какие услуги | водоснабжение, водоотведение, электроэнергия, три строки ОДН по воде и электро, техобслуживание МОП, капремонт. **Тепло и ОДН тепло — всегда одной строкой** (тариф — по позициям счёта-фактуры поставщика) |
| Порядок | строки одной услуги идут подряд, по датам; дальше — следующая услуга |
| Название | `name` у всех строк услуги одинаковое; даты показывать рядом с названием из `from`–`to`: «Водоснабжение (01.08.2026–15.08.2026)», «Водоснабжение (16.08.2026–31.08.2026)» — так строку подписывают квитанция стенда и Excel |
| Объём, тариф, сумма | `volume`, `tariff`, `amount` — каждой строки свои, показывать как есть; `volume × tariff`, вверх до копейки, = `amount`. В ЭК объём — площадь, `share` — доля дней этого тарифа (дни тарифа ÷ дни месяца) |
| Итог | сумма услуги — сумма её строк; `linesTotal` — сумма всех строк документа, как всегда |
| Один тариф на все дни квитанции | одна строка без `from`/`to`, тариф — тариф этих дней (а не средний за месяц): например, квитанция прежнего собственника за 01–09.08 при смене тарифа 16.08 — одна строка по старому тарифу |
| Сумма 0 | строка с суммой 0 (разграничено — `zero`, расхода не было) в обычной квитанции — одна, без дат |
| Доля счёта поставщика | `supplierShare` (месяц продажи) — у первой из строк услуги; объём доли в нём — за все дни документа |
| Корректировочная `/К1` | так же: строки по тарифам части. Корректировки, оформленные до 05.10.2026, — одной строкой по среднему тарифу месяца |

Пример (копия базы, август: водоснабжение 425,11 → 467,62 ₸ без НДС с 16.08, техобслуживание МОП 698 → 767,80 ₸/м² с 21.08),
помещение НП7, 126 м²:

| Строка | `from`–`to` | Объём | Тариф | Сумма |
|---|---|---|---|---|
| Водоснабжение | 01.08–15.08 | 3,42919 м³ | 493,1276 | 1 691,03 |
| Водоснабжение | 16.08–31.08 | 3,6578 м³ | 542,4392 | 1 984,14 |
| Водоотведение | — | 7,087 м³ | 628,546 | 4 454,51 |
| Техническое обслуживание МОП (м2) | 01.08–20.08 | 126 м² × 0,6451613 | 698 | 56 740,65 |
| Техническое обслуживание МОП (м2) | 21.08–31.08 | 126 м² × 0,35483871 | 767,80 | 34 328,10 |
| Взносы на капитальный ремонт | — | 126 м² × 1 | 35 | 4 410,00 |

Кабинет не должен рассчитывать на ровно восемь строк КУ и две ЭК и не должен склеивать строки одной услуги: собственник
сверяет каждую строку на калькуляторе.

## 3. Экраны кабинета

### 3.1 Мои помещения

| Что показать | Откуда | Заметки |
|---|---|---|
| Номер | `units.n` (в выгрузке — `unit`) | номер не меняется никогда, на нём держатся все ссылки |
| Этаж | `units.fl` | |
| Тип | `units.t` | «Апартамент жилой», «Нежилое, офис», «Нежилое, этажи 3–4», «Коммерческое» |
| Площадь, м² | `units.area` | в квитанции закрытого месяца — `area` документа (площадь, по которой считан месяц) |
| В управлении сейчас | `programs` (см. 3.3) | `units.prog`, `cno`, `cdt` — копия последнего договора, брать из `programs` |
| Какие помещения «мои» | `owners`: записи этого собственника, действующие на сегодня | ключа собственника нет — см. пробел 5 |

Не показывать: `units.inodn` (служебное поле расчёта), таблицу `unit_names` (служебные подписи оператора). Помещение с
пометкой `del` помечено на удаление и в расчёте не участвует.

### 3.2 Собственник и срок владения

| Что показать | Откуда | Заметки |
|---|---|---|
| ФИО | `owners.fio` | только на этом экране; в квитанциях ФИО нет |
| Владеет с | `owners.from` | пусто — «с начала учёта» |
| Владеет по | `owners.to` | пусто — владеет сейчас. Даты включительно: прежний собственник владеет по день до передачи, новый — с дня передачи |
| Телефоны, e-mail | `owners.phones[]`, `owners.emails[]` | в выгрузке нет |
| Представители | `owners.reps[]`: `fio`, `phones`, `emails`, `basis` (основание) | в выгрузке нет |
| Квитанции какого собственника | выгрузка: `from`–`to` документа сопоставить с `owners.from`–`to` | в месяц продажи две квитанции, `/1` и `/2`, `splitReason: owner-change` |

Запись с пометкой `del` помечена на удаление, её не учитывать. У одного помещения бывает несколько записей —
упорядочить по `from`.

### 3.3 Договор управления — программа, кто платит

| Что показать | Откуда | Заметки |
|---|---|---|
| Программа | `programs.prog`: `hybrid` — гибридная, `trust` — доверительная, `share` — долевая | нет записи, действующей на дату, — «не в управлении» |
| Номер и дата договора | `programs.cno`, `programs.cdt` | |
| Действует с / по | `programs.from`, `programs.to` | `to` пусто — действует |
| Программа и договор в квитанции месяца | выгрузка, `management` (`program`, `contractNo`, `contractDate`, `from`) | для закрытого месяца — как в снимке месяца |
| Кто платит по квитанции | выгрузка, `payer`: `owner` / `company` / `deduction` | в стенде слова: «собственник», «платит УК», «из доли» |

Кто платит, кабинет из программы сам не выводит: плательщик зависит не только от программы. Брать готовый `payer`
документа. Записи `programs` с пометкой `del` не учитывать.

### 3.4 Договоры разграничения с поставщиками

Такой договор значит, что собственник платит поставщику напрямую по своему договору. Поставщик определяется ресурсом:
вода — Су-Арнасы, электро — АРЭК, тепло — Теплотранзит.

| Что показать | Откуда | Заметки |
|---|---|---|
| Ресурс | `contracts.res`: `w` — вода, `e` — электро, `h` — тепло | |
| Номер договора | `contracts.no` | пусто — «№б/н» |
| Дата договора / с какой даты | `contracts.from` | |
| По какую дату | `contracts.to` | пусто — действует. `autoClosed` — дата, которой договор закрыт при продаже помещения |
| Акт опломбировки (только вода) | `contracts.seal` — дата акта, `contracts.sealNo` — номер | у электро и тепла акт не нужен. `actDel` — акт помечен на удаление, т. е. акта нет |
| «По факту» | `contracts.fact` | `true` — договор отмечен без номера и даты (в стенде так и пишется: «по факту») |
| Чей договор | `contracts.owner` — ФИО собственника, который заключил договор | заполнено не у всех |
| Сканы договора и акта | `contracts.files[]`: `id`, `name`, `type`, `size`, `part` (`dog` — договор, `act` — акт), `del`; сам файл — `GET /api/files/<id>` | см. пробел 10 |
| Что было в квитанции месяца | выгрузка, у строки с суммой 0 — `zero` | ниже |

Договор с пометкой `del` не показывать. Служебные поля не показывать: `checked` (отметка проверки оператором), `byDays`
(не используется), `note` (описание для оператора, см. пробел 10).

**В квитанции месяца (выгрузка).** Если объём этой услуги за дни квитанции ушёл поставщику, у строки `water_supply`,
`water_drainage`, `electricity` или `heat` сумма 0 и есть поле `zero`:

| Поле `zero` | Что это |
|---|---|
| `reason` | `direct` — «собственник платит поставщику напрямую»; `supplier_paid_by_company` — «счёт поставщика оплачивает УК (в управлении)»; `supplier_paid_from_share` — «счёт поставщика оплачивает УК, удерживается из доли» |
| `supplier` | Су-Арнасы / АРЭК / Теплотранзит |
| `contractNo`, `contractDate` | номер и дата договора |
| `effectiveFrom` | с какой даты действует (по воде — дата акта) |
| `actNo`, `actDate` | только вода: номер и дата акта |
| `byFact` | договор «по факту», без номера и даты |
| `manual` | разграничение отмечено оператором вручную |

Причину показывать рядом со строкой, иначе собственник будет звонить и выяснять. Если сумма 0 и `zero` нет — это обычный
ноль (расхода не было), пояснение не выдумывать. У строк ОДН `zero` не бывает.

**Месяц продажи** (схема 1.1). В квитанции нового собственника у строки услуги сумма не 0, и есть поле `supplierShare`:
`reason: previous_owner_contract`, `supplier`, `contractNo` и `contractDate` договора прежнего собственника, `days` и
`daysInMonth`, `volume`, `note` (готовое пояснение). Строку показать как обычную и добавить пояснение из `note`.

### 3.5 Квитанции месяца — коммунальная и эксплуатационная

Всё берётся из выгрузки закрытого месяца (`status: closed`).

| Что показать | Поле выгрузки |
|---|---|
| Номер квитанции | `code` |
| Вид | `type` (КУ / ЭК); у КУ — `kind` |
| Помещение, площадь | `unit`, `area` |
| За какой период | `period`, `from`–`to`, `days` из `daysInMonth`; если месяц поделён — «часть `part` из `parts`» |
| Когда выставлена, срок оплаты | КУ — `issueMonth`; ЭК — `issueDate`, `dueDate` |
| Кто платит | `payer` |
| Договор управления | `management` |
| Строки: услуга, объём, ед., тариф, сумма | `lines[]`: `name`, `volume` (у ЭК ещё `share`), `unit`, `tariff`, `amount`; если у строки есть `from`/`to` — даты рядом с названием: «Водоснабжение (01.08.2026–15.08.2026)» (см. раздел 2, «Строка на каждый тариф») |
| Пояснения к строкам | `lines[].zero`, `lines[].supplierShare` (см. 3.4) |
| Итого по строкам | `linesTotal` |
| Округление | `rounding` |
| К оплате | `total` |
| Переплата | `overpayment` (только если есть); тогда в квитанции «К оплате 0» и строка «Переплата» |

Каких собственнику показывать квитанции: в его квитанциях `payer: owner`, а даты `from`–`to` лежат внутри его владения.
Квитанции с `payer: company` и `deduction` по контракту уходят в отчёт собственнику (расчёт выплаты), а не в оплату (см.
раздел 4 и пробел 8).

### 3.6 Перерасчёт за прошлые месяцы

Если закрытый месяц исправили, разница может прийти строкой в квитанцию следующего месяца (в стенде это «способ Б»).

| Что показать | Откуда | Заметки |
|---|---|---|
| Строка «Перерасчёт за …» | выгрузка того месяца, где строка выставлена: `lines[]` с `code: recalc` | `name` — готовый текст: «Перерасчёт за июнь 2026 — разграничение по воде, договор №… с …», «Перерасчёт ЭК за …». ФИО в нём нет |
| Сумма | `amount` | целые тенге: плюс — доплата, минус — уменьшение |
| В какой квитанции | КУ или ЭК, по документу, где стоит строка | |

Объём, тариф и единица у этой строки — `null`. За какой месяц и по какой корректировке перерасчёт, видно только из текста
`name` (пробел 7). Внутри стенда источник — таблица `adjustments`, записи `invoices[]` с `kind: next-period`. После
закрытия месяца строка лежит в снимке: `closed_periods[].units[n].recalc`. В обоих местах есть ФИО, поэтому в кабинет их
отдавать как есть нельзя.

### 3.7 Корректировочные квитанции /К1

Если закрытый месяц исправили отдельным документом (в стенде это «способ А»), в выгрузке этого же закрытого месяца
появляется корректировочная квитанция. Она заменяет прежнюю.

| Что показать | Поле выгрузки | Заметки |
|---|---|---|
| Номер | `code`: `КВ-5017-2026-06/К1`, `ЭК-…/К1`; если месяц поделён — `/1К1`, `/2К1` | номер у каждого документа свой: смена собственника или плательщика с 1-го числа — аннулирующая прежнему `/1К1`, новая другому `/2К1` (до 05.10.2026 обе получали `/К1`) |
| Что заменяет | `corrective.replaces[]` — номера заменённых квитанций | вторая корректировка заменяет первую: у `/К2` в `replaces` стоит `/К1` |
| Исходная квитанция | `corrective.original[]` | |
| Заменена ли сама | `corrective.replacedBy` | есть — значит, уже не действует и показывается историей |
| Почему | `corrective.reason` | готовый текст без ФИО: «показание Электро 306386: 2 276,14 → 2 286,14», «смена собственника с 15.06.2026» |
| Когда | `corrective.issuedAt` (ISO) | |
| Было к оплате | `corrective.replacedTotal` | |
| Разница | `corrective.difference` | целые тенге: плюс — к доплате, минус — к зачёту |
| Изменение переплаты | `corrective.overpaymentChange` | если квитанция была в минусе, доплата сначала уменьшает переплату |
| Аннулирующая | `corrective.annul: true` | все строки нулевые (у КУ объём 0, у ЭК доля `share` 0 — «площадь × тариф × доля» = 0); выставляется прежнему плательщику, когда плательщик сменился задним числом. Новому плательщику в этом случае приходит отдельная корректировочная с пустым `replaces` |
| Номер корректировки и группы | `corrective.adjustment` (`ADJ-…`), `corrective.group` (`ADJG-…`) | для журнала и связи |
| Строки и итоги | как у обычной: `lines`, `linesTotal`, `total`, `rounding`, `overpayment` | строки `recalc` и `offset` заменённой квитанции остаются; может быть строка `manual` — «Корректировка суммы»; если тариф менялся в днях квитанции — строка на каждый тариф с `from`/`to`, как у обычной (с 05.10.2026); ноль с причиной (`zero`) — как у обычной (с 05.10.2026) |

Корректировочную показывать вместо заменённой, а заменённую хранить и показывать историей. Пример из проверки 03.10.2026:
`КВ-5017-2026-06/К1`, к оплате 38 866 вместо 38 488, `difference` 378.

### 3.8 Зачёт переплаты

| Что показать | Откуда | Заметки |
|---|---|---|
| Строка «Зачёт переплаты» | выгрузка месяца, где сделан зачёт: `lines[]` с `code: offset` | `name` — «Зачёт переплаты» или «Зачёт переплаты — примечание» |
| Сумма | `amount` | минус, целые тенге |
| В какой квитанции | КУ или ЭК, по документу | |

Сам по себе зачёт не делается: оператор вносит его кнопкой в стенде, и только в квитанцию открытого месяца. Внутри
стенда источник — таблица `offsets`, записи `type: KU` или `EK` (`id`, `unit`, `fio`, `amount` — положительное число,
`period`, `type`, `note`, `at`, `by`). После закрытия месяца зачёт лежит в снимке: `closed_periods[].units[n].offsets`.

### 3.9 История начислений по месяцам

| Что показать | Откуда | Заметки |
|---|---|---|
| Месяцы | выгрузки всех закрытых месяцев (`period`) | кабинет складывает их у себя: запроса «история помещения» нет |
| КУ и ЭК за месяц, к оплате | документы помещения (`unit`): `type`, `total` | если месяц поделён — несколько документов (`/1`, `/2`) |
| Переплата за месяц | `overpayment` | |
| Исправления | корректировочные документы (`corrective`) | в сумму месяца — последняя корректировочная (без `replacedBy`) вместо тех, кого она заменяет; заменённые — историей |
| Перерасчёт и зачёт | строки `recalc` и `offset` | они стоят в том месяце, где выставлены, а не в том, за который перерасчёт |

Месяц закрыт, если в таблице `closed_periods` у него `status: closed`. Если `status: reopened`, месяц открыли заново, и его
прежний снимок остался только историей (`closed_periods[].history`). Снимок месяца (`closed_periods[].units`) содержит
ФИО и служебные поля расчёта, поэтому источником для кабинета он не годится (пробел 15).

### 3.10 Показания приборов

В выгрузке показаний нет: по контракту их туда не включают. Брать из таблиц.

| Что показать | Откуда | Заметки |
|---|---|---|
| Прибор | `meters`: `res` (`hvs` — холодная вода, `gvs` — горячая вода, `ee` — электроэнергия), `sn` — серийный номер | у тепла приборов нет |
| Коэффициент | `meters.k` | у электросчётчиков бывает больше 1 |
| Установлен / снят | `meters.from`, `meters.to` | ставит акт замены. В месяц замены в расчёте участвуют оба прибора |
| Начальное показание | `readings.prev` (`readings.meter` = `meters.id`, `readings.period` = ГГГГ-ММ) | |
| Конечное показание | `readings.cur` | |
| Расход | (`cur` − `prev`) × `k`; если получилось меньше 0 — 0 | так считает стенд (`meterUsage`) |
| Показание на дату передачи | `readings.ownRead` | заполнено, только если месяц поделён продажей |
| Замена прибора | `replacements`: `date`, `period`, `old` (`id`, `sn`, `final` — конечное), `new` (`id`, `sn`, `k`, `initial` — начальное), `note` | |

Не показывать прибор с `bill: false` («не участвует в расчётах», служебный или дублирующий) и прибор с пометкой `del`.
Служебные поля показаний — не для кабинета: `midRead` (не используется), `prevSrc` и `prevNote` (откуда взято начальное:
`carry` — конец прошлого месяца, `act:…` — акт замены, `adj:…` — корректировка, `manual` — вручную), `lockPrev` и
`lockCur` (зафиксировано актом).

**Расход прибора и объём в квитанции — разные числа.** Если прибор разграничен, месяц поделён или выставлена доля счёта
поставщика, в квитанции будет другой объём. Объём для квитанции берётся только из выгрузки.

### 3.11 Переплата и что с ней сделано

В стенде переплата учитывается по помещению и собственнику, и только по квитанциям, которые платит собственник
(`payer: owner`).

| Что показать | Выгрузка | Таблица стенда |
|---|---|---|
| Начислено — квитанция ушла в минус | у документа `overpayment` | `closed_periods[].credits[]`: `unit`, `fio`, `period`, `code` (номер квитанции), `type` (KU / EK), `amount` |
| Начислено — по корректировочной | `corrective.difference` (минус — к зачёту) и `corrective.overpaymentChange` | `adjustments[].credits[]`: те же поля и ещё `adj` (номер корректировки); `amount` со знаком |
| Зачтено в квитанцию | строка `offset` (см. 3.8) | `offsets`, `type: KU` / `EK` |
| Возвращено деньгами | нет | `offsets`, `type: REFUND`: `unit`, `fio`, `amount`, `date` (когда вернули), `month`, `note` (как вернули), `at`, `by` |
| Остаток | нет | начислено − зачтено − возвращено, так считает стенд. Переплата открытого месяца сюда попадает только после его закрытия |

Записи `credits` и `offsets` привязаны к собственнику по ФИО, а не по ключу (пробел 2).

## 4. Что важно соблюдать

- **В квитанции нет ФИО.** Документ выставлен на помещение. Тексты `name`, `corrective.reason`, `supplierShare.note`
  приходят уже без ФИО — не дописывать их туда. Чья квитанция, определяется по датам документа и таблице `owners`.
- **К оплате — целые тенге, округление вверх.** Каждая строка уже округлена вверх до копейки. `linesTotal` — сумма
  строк, `total` — это `linesTotal`, округлённый вверх до целого тенге. Кабинет не округляет сам и не считает итог
  иначе, чем сумму строк. При приёме сверить: сумма `amount` = `linesTotal`; если не сходится — запись в журнал,
  квитанцию всё равно показать.
- **Квитанция не уходит в минус.** Если сумма строк меньше нуля (перерасчёт или зачёт больше начисления), `total: 0`, а
  `overpayment` — переплата в целых тенге. Показывать «К оплате 0» и отдельной строкой «Переплата». Разница
  корректировочной (`difference`), доплата или зачёт, — тоже в целых тенге.
- **Помещение в управлении.** Это видно по полю `payer` у каждого документа, а не по помещению целиком.
  `company` — квитанцию оплачивает УК за собственника. `deduction` — оплачивает УК и удерживает из доли собственника.
  По контракту документы с `company` и `deduction` берёт расчёт отчёта собственнику (выплата), а квитанции к оплате в
  кабинете — это документы с `owner`. Месяц может быть смешанным: например, `/1` — `owner`, `/2` — `company`. Показывать
  ли такие документы собственнику для сведения, не решено (пробел 8).
- **Закрытый месяц не меняется.** Снимок закрытого месяца в стенде не меняется. Исправление приходит отдельным
  документом: корректировочной квитанцией `/К1` того же месяца (заменяет прежнюю, прежняя остаётся историей) или строкой
  «Перерасчёт за …» в квитанции следующего месяца. Ранее полученную квитанцию на месте не переписывать.
- **Черновик не показывать.** Файл с `status: open` — расчёт ещё не закрытого месяца.
- **Даты.** В выгрузке даты в виде ГГГГ-ММ-ДД, все включительно. В стенде на экране — день.месяц.год.

## 5. Пробелы — чего кабинету не хватает в нынешней выгрузке

По каждому пункту нужно решение заказчика: добавить в выгрузку или брать из таблицы. Решений здесь нет.

1. **Показания приборов.** В выгрузке их нет: так задано контрактом 17.09, раздел «Чего в контракте нет намеренно».
   В таблицах есть: `meters` и `readings`. Решить: добавить в выгрузку или брать из таблиц. Отдельно решить, какие
   показания закрытого месяца показывать: из снимка (как были на закрытии, `closed_periods[].units[n].det`) или
   нынешние из `readings` (после корректировки они могут отличаться).
2. **Учёт переплаты целиком.** В выгрузке есть только `overpayment` документа, `corrective.difference` /
   `overpaymentChange` и строки `offset`. Нет возвратов деньгами (`offsets`, `type: REFUND`) и нет остатка. В таблицах
   учёт привязан к собственнику по ФИО, а в выгрузке ФИО нет. Решить: добавить в выгрузку или брать из таблиц
   `closed_periods.credits`, `adjustments.credits`, `offsets` и по какому ключу.
3. **Список договоров разграничения.** В выгрузке они есть только у нулевых строк месяца (`zero`) и у `supplierShare`.
   Отдельного списка договоров помещения нет: поле `justification.directContracts` из проекта 17.09 не сделано. Нет
   готового признака «договор действует сейчас» — ни в выгрузке, ни в таблице `contracts` (стенд вычисляет его сам).
   Решить: добавить в выгрузку или брать из `contracts` и как показывать, действует ли договор.
4. **Кто платит сейчас.** `payer` и `management` есть только в документах выгрузки закрытого месяца. В таблицах есть
   программа (`programs`), но плательщика нет. Для текущего, ещё не закрытого месяца источника нет. Решить.
5. **Ключ собственника.** Ни в `owners`, ни в выгрузке нет кода собственника: `owner.id` из проекта 17.09 не сделан.
   Связать пользователя кабинета с его помещениями и документами сейчас можно только по ФИО и датам владения. Вход и
   роли делает разработчик кабинета. Решить, откуда берётся связь «пользователь → помещения».
6. **Выгрузка — за весь месяц целиком.** Файлом из браузера или запросом `GET /api/accruals?period=ГГГГ-ММ` (05.10.2026, тот
   же документ; `GET /api/export` с отборами из проекта 17.09 не сделан). Нет `changedSince` и нет уведомления о корректировках: новая
   корректировочная появится, только если месяц выгрузят повторно; перерасчёт строкой — в выгрузке следующего месяца.
   Решить, как кабинет узнаёт об изменениях.
7. **У строк перерасчёта и зачёта нет ссылок.** У `recalc` и `offset` нет полей «за какой месяц», «номер
   корректировки», «из какой переплаты» — всё только текстом в `name`. Решить, нужны ли такие поля.
8. **Квитанции «платит УК» и «из доли».** По контракту собственнику к оплате показываются документы `owner`, а
   `company` и `deduction` идут в отчёт собственнику. Показывать ли собственнику в управлении эти квитанции для сведения
   (с пометкой «оплачено УК» или «удержано из доли»), не решено.
9. **Переоткрытие месяца.** Если месяц открыли заново и закрыли снова, в выгрузке нет признака, что она заменяет
   прежнюю за тот же месяц. Есть только `generatedAt`. Решить, как кабинет заменяет ранее загруженные документы.
10. **Сканы и описание договора.** `contracts.files` (сканы договора и акта) и `contracts.note` (описание) есть только
    в таблице, в выгрузке их нет. Показывать ли их собственнику, не решено.
11. **Печать и PDF квитанции.** В стенде не сделаны.
12. **Оплаты, сальдо, долг.** Их нет ни в выгрузке, ни в таблицах стенда (контракт: «сальдо и оплаты» — намеренно
    нет). Оплата по QR — на паузе.
13. **Контакты собственника.** `owners.phones`, `emails`, `reps` есть только в таблице, в выгрузке их нет. Решить,
    нужны ли они кабинету и откуда.
14. **Текущий месяц.** Выгрузка открытого месяца — черновик. Показывать ли собственнику предварительные начисления до
    закрытия месяца, не решено.
15. **История начислений одним запросом.** Её нет. Кабинету придётся копить выгрузки по месяцам. Снимки
    `closed_periods` содержат ФИО и служебные поля расчёта. Решить источник истории.

## 6. Для пробы на стенде — запросы только на чтение

Стенд работает только на этом компьютере, без входа и прав. Ответы содержат ФИО, контакты и служебные поля. Эти запросы —
чтобы посмотреть данные. Кабинет не должен ходить в стенд: в продакшене у него свои запросы к тем же таблицам в БД.

| Запрос | Что отдаёт |
|---|---|
| `GET /api/state?period=ГГГГ-ММ` | всё сразу: помещения в собранном виде (`owners` с контактами, `meters` с показаниями месяца и всех месяцев в `hist`, `rz` — договоры разграничения по ресурсам `w` / `e` / `h`, `progs` — договоры управления), тарифы, переплаты `credits`, зачёты и возвраты `offsets`, корректировки месяца `adjustments`; для закрытого месяца — ещё снимок `closed` целиком |
| `GET /api/unit/<номер>?period=ГГГГ-ММ` | одно помещение в собранном виде |
| `GET /api/table/<имя>` | таблица целиком: `units`, `owners`, `programs`, `contracts`, `meters`, `readings`, `replacements`, `closed_periods`, `adjustments`, `offsets`… |
| `GET /api/period/<ГГГГ-ММ>` | закрыт ли месяц (`closed` — заголовок снимка), список закрытых, корректировки и переносы месяца, `credits`, `offsets`; с `?full=1` — снимок целиком |
| `GET /api/adjustments?period=ГГГГ-ММ&unit=<номер>` | корректировки (оба параметра необязательны) |
| `GET /api/offsets` | зачёты переплаты и возвраты деньгами |
| `GET /api/files/<id>` | скан из вложений договора |
| `GET /api/accruals?period=ГГГГ-ММ` | выгрузка квитанций за весь месяц — тот же документ, что «Для кабинета: JSON» (схема 1.6): закрытый месяц — из снимка (`status: 'closed'`), открытый — черновик (`'open'`); ФИО в нём нет. Ошибки: 400 — нет месяца или не `ГГГГ-ММ`, 404 — месяца в стенде нет, 500 — «Выгрузка остановлена — в данных ошибка» со списком `errors` |

Выгрузка квитанций — и файлом из браузера стенда, и запросом `GET /api/accruals` (с 05.10.2026); содержание одно и то же.
